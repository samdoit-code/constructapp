## 1A. Project Overview

**What it is:** A mobile-first business management app for a Brazilian construction company (Construtora Moreira), covering expense tracking (Caixa da Obra), contractor/labor payments (Empreiteiro), tasks, notes, photos, and documents — organized per construction project (e.g., "Obra Gavião", "Obra Boreal").

**Who uses it:** The owner's family/business partners, primarily on iPhone as a home-screen installed PWA, with occasional desktop browser use for administration.

**Production status:** Live and in active use. Hosted on GitHub Pages at `https://samdoit-code.github.io/constructapp/`. Data has been migrated from a manually-maintained Excel spreadsheet (~3,000 historical entries). The app is under active, incremental development — not a finished/frozen product.

**Reusability goal (explicitly established):** This app is intended to become a reusable template/foundation for future internal business apps built on the same stack (HTML/JS → Google Apps Script → Google Sheets + Drive). The authentication/authorization block in particular was deliberately designed to be generic and portable, not app-specific.

## 2. Current Tech Stack

- **Frontend:** Single self-contained `index.html` file — HTML/CSS/JS, no framework, no build step, no bundler. All JS is inline in one `<script>` tag wrapped in an IIFE.
- **Backend:** Google Apps Script (`backend/Code.js`), deployed as a Web App (`doGet`/`doPost`).
- **Database:** Google Sheets — one spreadsheet holds business data (tabs: Projetos, CaixaObra, Empreiteiro, Tarefas, Notas, Fotos, Documentos, Tipos, Unidades). A **separate** spreadsheet holds user/role/permission data (tabs: `Usuarios` for identity, `Papeis` for role capabilities), intentionally isolated from business data for defense-in-depth.
- **File/photo storage:** Google Drive, organized as project-specific subfolders under a parent "Construtora Moreira" folder, plus a `Backups` subfolder for automated daily spreadsheet backups.
- **Authentication:** Google Identity Services (GIS) — the Sign-In/One-Tap API (`google.accounts.id`), not the separate OAuth token-client API.
- **Hosting/deployment:** Frontend on GitHub Pages (static). Backend via Apps Script's own Web App deployment mechanism (URL stays stable across "new version" deploys).
- **Service worker (`sw.js`):** deliberately network-first, not cache-first — it only serves its cached copy of `index.html`/assets when a fetch genuinely fails (true offline), never to mask a slow-but-successful network response. Registered lazily on `window.load` (`index.html`, near the bottom of the script) so it never competes with the initial page load.
  - **What it caches:** only same-origin `GET` responses that reach the end of its three filters — non-`GET` requests, cross-origin requests, and `version.json` are all excluded *before* any cache logic runs (`sw.js`'s `fetch` handler). In practice that means `index.html` (always normalized to the single key `./index.html` for every navigation, including a cache-busted `forceAppReload()` reload — see below) plus whatever static files under `/assets/` happen to be requested.
  - **What it never caches, by construction:** the Apps Script backend (cross-origin — excluded outright), `version.json` (excluded by name, must always hit the network for `checkForUpdate()`), any `POST` request (writes never pass the method filter), and therefore any Sheets/Drive data or authenticated response. There is no IndexedDB, no background-sync, and no offline write queue anywhere in this app — offline gives you whatever `localStorage`'s `cmoreira_cache_v1` last had, never the ability to create/edit/delete while disconnected.
  - **Why network-first specifically:** an online user must always get whatever is actually live right now. The cache is a fallback for a genuinely failed fetch, never a first stop — this is what guarantees the service worker can't be the reason someone sees stale content after a real deploy, and why `forceAppReload()`'s cache-busted URL (`?_r=<timestamp>`) still forces a real network fetch through it rather than being served from cache.
  - **Reusable pattern for future apps on this stack:** if a service worker is added at all, keep it to exactly this scope — an app-shell fallback for a true offline launch, network-first, with an explicit denylist for anything that must always be live (a version-check file, the backend origin, non-GET requests). Do not reach for cache-first or a more aggressive precache list without re-verifying the update-check/force-reload path (`checkForUpdate()`/`forceAppReload()`/`visibilitychange` in `index.html`) still bypasses it — that combination is what keeps "add offline tolerance" from quietly becoming "sometimes serves an old build to an online user." If offline writes are ever wanted, that's a distinct feature (IndexedDB + a retry queue + conflict handling against the existing `lastModified` check) — not a natural extension of this file, and deserves its own design pass rather than being bolted onto the shell cache.
- **Static assets** (logo, generated PWA/iPhone icons, web manifest) live in `/assets`, referenced from `index.html` by relative path. See `assets/README.md` for how the icon set (solid orange background, white logo) and the white header/sign-in logo variant were derived from the original logo. Both a Lottie-based sign-in animation and a follow-up plain-CSS "logo pieces assemble" animation were tried and reverted — neither read well in practice — so the sign-in screen intentionally uses a plain static logo on a flat background. Don't reintroduce motion here without being asked.
- **`apple-mobile-web-app-capable` / `apple-mobile-web-app-status-bar-style` are deliberately NOT set.** They were tried once, changed how iOS computes the safe-area/viewport for the home-screen PWA, and caused a blank gap below the bottom tab bar. Re-test thoroughly on an actual iOS device before reintroducing either.

## 2A. Source Control, Branching & Deployment

- **Source control:** Git, hosted on GitHub at `samdoit-code/constructapp`.
- **Production branch:** `main`.
- **Default workflow: commit and push directly to `main`.** This project has one active maintainer (via Claude Code) and no review step in practice — a "develop on a branch, open a PR later" workflow only created a place for finished work to be silently forgotten. That happened for real: a full audit's worth of fixes, security work, and the PWA icon set sat on an unmerged branch for weeks while `main` kept serving old code, because nothing forced the merge to happen. Direct-to-main removes the failure mode structurally — there is no branch left to forget.
- **When a branch is still appropriate:** a change large or risky enough that you want to inspect the whole diff before it goes live (e.g. an architectural change, something explicitly flagged as needing confirmation first). Even then, the branch must be merged into `main` (or explicitly abandoned and deleted) in the **same session** — never left open across sessions "to merge later." If a session ends with an unmerged branch, treat that as an incomplete task, not a paused one.
- **Before starting new work each session, check for drift:** `git fetch origin && git log origin/main..origin/<any-other-branch>` (or just glance at the repo's branch list) — if anything beyond `main` carries commits not on `main`, surface it before doing anything else, the same way this was caught during the audit. A scheduled check (`.github/workflows/branch-drift-check.yml`) also does this automatically and fails visibly in the Actions tab if a branch goes stale.
- **GitHub is the source of truth:** The repository contains the authoritative frontend and backend source files. Do not treat manually edited production files as the canonical source.
- **Frontend deployment:** GitHub Pages automatically builds/deploys the frontend from the repository.
- **Backend deployment:** `.github/workflows/deploy-backend.yml` automatically deploys the Apps Script backend using Google `clasp` — it both pushes the source (`clasp push`) AND redeploys the live Web App to that new code (`clasp update-deployment`, targeting the one existing deployment so the `/exec` URL never changes). See Section 7 for why the second step matters and isn't optional, and for the `clasp push --force` / push-output assertion that keeps a green job from silently deploying nothing.
- **Backend deployment trigger:** Changes to `backend/**` pushed to `main` trigger the Apps Script deployment workflow.
- **Frontend and backend deployment are independent:** A frontend-only change should not require an Apps Script deployment, and a backend-only change should not require a frontend deployment.
- **CI/CD:** GitHub Actions is used for automated deployment. Do not manually copy `Code.js` into the Apps Script editor when the change is already committed to the repository.
- **Production:** `main` represents the production-ready source. GitHub Pages and the Apps Script deployment workflow publish the corresponding frontend/backend changes after they reach `main`.

## 3. Architecture

### Frontend ↔ Backend communication
- Frontend calls the Apps Script Web App via `fetch()`.
- **Reads and writes are both `POST`**, with `Content-Type: text/plain;charset=utf-8` — **deliberately not `application/json`**, because Apps Script does not handle the CORS preflight that a JSON content-type would trigger. `Code.js` parses the raw body as JSON manually on its side. Reads (`action=getAll`) used to be a `GET` with `idToken` as a query param; this was changed (see Security below) so the bearer token never travels in a URL. `doGet` is now an intentional no-op — do not resurrect a GET-based read path.
- The Apps Script Web App URL and `GOOGLE_CLIENT_ID` are configured as constants near the top of the frontend `<script>` and near the top of `Code.js`. They must match exactly between the two files (case-sensitive, no typos) — a mismatch was the root cause of a real production auth failure once already.

### Apps Script ↔ Sheets/Drive
- `Code.js` is a **container-bound** script (opened via Extensions → Apps Script from inside the business-data spreadsheet), so it accesses that spreadsheet via `SpreadsheetApp.getActiveSpreadsheet()` with no explicit ID needed.
- The **separate** `Usuarios` auth spreadsheet is accessed via `SpreadsheetApp.openById(AUTH_SHEET_ID)` — a different spreadsheet than the one the script lives in.
- Drive files are currently uploaded with `DriveApp.Access.ANYONE_WITH_LINK` / `Permission.VIEW` sharing (see Known Limitations — this is an accepted, flagged, not-yet-fixed gap, not an oversight).
- **A project's Drive folder is resolved BY NAME, not looked up in a hardcoded ID map.** `PROJECT_FOLDERS` in `Code.js` still exists but only for the two folders that predate this — `findProjectFolder_`/`resolveOrCreateProjectFolder_` check that map first, then look for (or create) a same-named subfolder under `FALLBACK_FOLDER_ID`. Without this, a project added or renamed through the app's own Settings screen had no entry in the map and every one of its uploads silently fell through to the shared fallback folder forever. **Reusable pattern:** never hardcode a per-tenant/per-entity resource ID in backend source when it can be resolved from data the app already manages — a new entity created through the app's own UI must be a *complete* operation, not one that quietly degrades a feature the UI otherwise presents as fully supported.
- **A project's canonical Drive folder id is now BACKEND-OWNED, persisted in `Projetos.driveFolderId`, and resolution is ID-first.** Name-only resolution (the bullet above) meant a person renaming a project's folder directly in Drive — nothing stops that, Drive has no concept of "this app manages this folder" — silently broke every future lookup: `deleteProject_` would find nothing to trash (leaving every file behind), and a rename would rename the wrong thing or nothing. `resolveProjectFolderById_` reads the project's stored id and calls `DriveApp.getFolderById()` directly; `resolveOrCreateProjectFolder_` tries that FIRST, and only falls back to the old name search (still under the same lock, so a lookup-or-create race still can't create two folders) for a project that has never had a folder resolved through this path — then **persists whatever it finds or creates**, via a single targeted cell write (`persistProjectFolderId_`), never a whole-tab rewrite. `deleteProject_` and `renameProject_`'s cosmetic Drive step both resolve by id the same way now (capturing the folder *before* the Projetos row's id/existence is touched, since the id lookup needs the row intact). **No migration script exists or is needed** — this is a self-healing backfill: an existing project's `driveFolderId` starts blank and gets filled the next time anything touches its folder (an upload, a rename, a delete), and until then it behaves exactly as it always has (name fallback). A stored id that no longer resolves (folder trashed/deleted directly in Drive) is deliberately **not** treated as "try a name guess instead" — that could silently attach to an unrelated folder that happens to now hold the project's name. **This is enforced by `lookupProjectFolder_`, which returns an explicit STATE rather than a folder-or-null** (`unset` = never backfilled, a name search IS legitimate; `stale` = stored id no longer resolves; `trashed` = it resolves but sits in the Drive trash; `resolved` = usable). That distinction is load-bearing and was learned the hard way: for a while every caller wrote `resolveProjectFolderById_(x) || findProjectFolder_(x)`, and that `||` silently reinstated the exact name guess the null return existed to prevent — an upload would attach to a same-named stranger AND `persistProjectFolderId_` would overwrite the canonical id with that guess, permanently. An upload against a `stale`/`trashed` canonical id now **throws** (`pasta do projeto indisponível no Drive`) rather than guessing or writing into a trash tree that Drive purges after 30 days; `deleteProject_` skips the Drive step and reports `driveFolderUnresolved`; `renameProject_` skips its cosmetic rename. **Reusable pattern:** when "couldn't resolve" has two causes that demand opposite handling, never let the function return a single falsy value for both — the caller will inevitably `||` its way back to the wrong branch.
  - **This is backend-owned specifically because `Projetos` is a whole-tab-replace sheet and the client has no concept of the column at all.** The frontend's `projects` array is `{id, name}`, and `toSheetRows('projects', ...)` always emits `{id, ativo}` — it was never going to carry a folder id through a save, which means the ordinary "add a project" flow (`saveKey('projects', projects)`, sending the ENTIRE array) would blank every other project's already-resolved `driveFolderId` on every add or rename, using nothing more than staleness the client can't see (its in-memory copy predates whatever the backend persisted since the last `getAll`). `saveProjetos_` (via `preserveProjectFolderIds_`) reads the sheet's own current values and stamps them back onto whatever the client sent, keyed by id, before writing — the client's payload for this column is never trusted, because it never sends one. **Reusable pattern:** when a whole-tab-replace sheet grows a column the client's own data model doesn't (and shouldn't) know about, the column can only survive client-driven saves if the backend actively re-merges it in — never assume "the client didn't touch it" is the same as "the client's payload is safe to write as-is."
  - **`deleteProject_` resolving by id, not name, means it structurally cannot widen into deleting a same-named duplicate** — it only ever trashes the one folder its stored (or freshly resolved) id points to. That leaves a genuine question unanswered: what about a duplicate, or a folder orphaned by a project deleted before any of this existed? `auditProjectFolders()` answers it as a **strictly read-only** report (no `commit` argument at all, unlike `sweepOrphanFiles`/`mergeDuplicateProjectFolders`) — for every folder under `FALLBACK_FOLDER_ID`, classifies it as canonical (id matches a live project), a **duplicate** (shares a live project's name but not its id), or **orphaned** (matches no live project by id or name), with enough per-folder detail (name, id, created date, immediate file count, and each subfolder's name + file count) for an admin to decide by hand. Deliberately does not auto-merge or auto-trash anything it finds — "same name" was already shown (by the very race this column exists to route around) to not be sufficient signal to safely automate a choice between two folders.
- **A check-then-create against Drive must be locked, even outside the write lock, or concurrent requests create duplicates.** `resolveOrCreateSubfolderLocked_`/`resolveOrCreateProjectFolder_` wrap their `getFoldersByName` → `createFolder` sequence in a short-lived `LockService` lock — held only for that lookup-or-create, never for the upload itself, so it doesn't reintroduce the throughput problem moving `uploadFile` out of the write lock was fixing (see below). Without it, the first batch of uploads to a project's `Fotos/` folder raced: 3 concurrent workers each saw "no Fotos folder yet" and each created their own, because Drive has no uniqueness constraint on folder names within a parent. Reproduced live: one project ended up with 3 separate "Fotos" folders after a single batch, with uploads scattered across all three. **Two follow-on defects came from the same root cause:** `sweepOrphanFiles` used `getFoldersByName(...).next()` — grabbing only the *first* matching folder — so orphans sitting in the other duplicates were permanently invisible to it (a Drive full of visible leftovers still swept to zero); fixed by scanning every folder the name matches, not just the first. And the duplicates already created before the fix needed a one-time repair, `mergeDuplicateProjectFolders(commit)` — same dry-run-by-default shape as the sweeper — which keeps the OLDEST same-named folder as canonical, moves every file out of the others into it (`addFile`/`removeFile`, never a delete), and trashes the emptied duplicates. **Reusable pattern:** any time code does "look for X, create X if missing" against a system with no uniqueness constraint (Drive folder names, but the shape recurs elsewhere), that sequence needs a lock around it the moment more than one execution can reach it concurrently — and a scanner built to consume the result (like the sweeper) must never assume the lookup step enforced uniqueness that was never actually guaranteed.
- **Every project folder has its own `Fotos/`/`Documentos/` subfolders, resolved on an explicit `kind`, never inferred.** `resolveOrCreateSubfolder_(parentFolder, name)` creates/finds a same-named child folder the same way `resolveOrCreateProjectFolder_` does at the project level, and `uploadFile` picks between them using a `kind` field (`'photo'` | `'doc'`) the frontend sends alongside `section` — a **separate** field, deliberately, not derived from `section` (a photo and a document can share the same section, e.g. both `docs` for a project-level photo vs. a project-level document) and not from `mimeType` (a scanned receipt uploaded through "Adicionar documento" is legitimately an image that still belongs in `Documentos/`, not `Fotos/`). An unrecognized or missing `kind` falls back to the project root rather than guessing, so an old, not-yet-redeployed frontend still uploads successfully. **No migration of existing files was done or is planned** — every reference in the app is by `driveFileId` (`photoEmbedUrl`, `pdfEmbedUrl`, `deleteFile`), so where a file physically sits has zero effect on app behavior; this only changes where *new* uploads land. **Reusable pattern:** when a resource needs sub-categorization by an app-level concept (here: photo vs. document) that doesn't already have its own reliable signal in the request, add that concept as its own explicit field — don't try to reverse-engineer it from a field that means something else (`section`) or from incidental data (`mimeType`).

### Data flow (frontend)
- **An empty project list is a legitimate state the whole UI must render, never a crash and never something to paper over with invented data.** `applyServerData_` used to substitute a hardcoded `[Obra Gavião, Obra Boreal]` whenever the server returned zero projects — written back when reaching zero was impossible. `deleteProject_` made it reachable, and the result was worse than an empty screen: the app showed two projects that did not exist, and the next whole-tab Projetos save (adding a project sends the ENTIRE array) wrote both of them into the sheet for real. Separately, `finishLoadSetup`'s `projects[0].id` threw a TypeError on an empty list, which propagated out of `loadAll()` and surfaced as a generic "Não consegui entrar. Tente novamente." — a permanent, unrecoverable sign-in loop, because the cache that caused it was never cleared. Both are fixed, and `onGoogleSignIn` now drops the cache on ANY sign-in failure, not just an auth one: if the cached data itself is what broke the boot, keeping it guarantees the next attempt breaks identically. **Reusable pattern:** an invented default is a lie the persistence layer will eventually believe — render the empty state instead, and never let a failed boot preserve the thing that failed it.
- **Cache-first load, gated by a cheap authoritative auth check.** Sign-in does **not** wait for `getAll`. `onGoogleSignIn` first calls a dedicated `verify` action (backend returns `{currentUser}` only — no sheet data at all, no script lock), which establishes identity *and* the live `sections`/`projects` on a request that touches no spreadsheet. Only then does `loadAll()` run: if a `localStorage` cache (`cmoreira_cache_v1`) exists, the app filters it against those just-verified permissions, opens the gate, and renders immediately, then hydrates from `getAll` in the background and re-renders. With no cache on the device it still awaits `getAll` and a failure is still a hard sign-in failure. **The measured effect: the gate opens in ~15–25 ms after the credential arrives even with `getAll` artificially stubbed at 4 s** — the metric is *time until the user can act*, not total load duration.
  - **Security rule, non-negotiable: cached data must never be rendered against stale permissions.** `filterCacheAgainstCurrentPermissions()` runs *before* the cached state is ever drawn, and filters on **both** axes using the `currentUser` that the fresh `verify` just returned — never the `currentUser` that was embedded in the cache. Rows whose section lost `view`, and rows outside the user's current project scope, are dropped from the in-memory arrays first. Without this, a demotion (role change, project removed) would still show the old data on that device until `getAll` landed. **Reusable pattern:** any "render from local cache first" design must pair the cache with a cheap authoritative permission check on every boot, and re-filter the cache against *that* result — a cache is a performance store, never an authorization record. This is a courtesy filter on top of the real boundary as always: the backend still withholds the same data from `getAll` independently.
  - **A frontend shadow-check of a backend authorization rule must mirror its exact semantics, including edge cases — never be independently re-derived.** `filterCacheAgainstCurrentPermissions()`'s project filter initially treated a row with no resolvable project as "unrestricted, let it through," while the backend's actual authority, `hasProjectAccess_()`, does the opposite (`if (!projectName) return false`) — a project-scoped user is denied a project-less row, not waved through. The frontend copy was *more permissive* than the rule it existed to shadow: a project-less cached entry or task would render for the seconds between the gate opening and `getAll` replacing it, on a device belonging to a user the real backend would never have sent that row to. Fixed by making the frontend predicate match the backend one, condition for condition, not just for the common case. **Reusable pattern:** whenever a frontend courtesy check exists purely to make an authoritative backend rule feel instant (a cache filter, an optimistic UI gate, a "hide this button" check), treat the backend function as the spec and copy its edge-case behavior line by line — reasoning about what "should" happen for an edge case independently, even when it seems obviously safe, is exactly how the two drift apart.
  - **Backend warm-up:** `warmUpBackend()` fires a single throwaway `verify` `POST` on `pointerdown` of the Google sign-in button (once, best-effort, result ignored), so Apps Script's cold-start happens in parallel with the user completing the Google account picker instead of serially after it.
  - **The cache write is deferred, never blocking.** `saveCacheToLocalStorage()` serialises the whole dataset — hundreds of ms at a few thousand rows — so it is scheduled via `requestIdleCallback` (falling back to a macrotask on iOS Safari, which has no rIC) and coalesced behind a single `cacheWriteScheduled` flag. Nothing on screen depends on it having finished; if the app is closed before it runs, the next boot simply fetches. Do not make this synchronous again to "guarantee" a write.
- **Row-level writes with diffing:** the app keeps an in-memory snapshot (`sheetSnapshot`) of what was last synced per tab. Saves diff the current state against that snapshot and send only the changed/deleted rows (via a `batchMulti` action), not a whole-tab rewrite. This is wrapped behind a stable `saveKey(key, value)` function used by ~30 call sites throughout the app — call sites never changed when the underlying sync mechanism was rewritten from whole-tab to row-level.
- **`syncSheets()` (the function every `saveKey` write ultimately calls) is serialized through a global FIFO queue (`syncQueue`), not fired freely.** `diffRows_()` computes what to send by reading `sheetSnapshot` at the moment it runs, and the snapshot is only updated once THAT call's own response lands — so two overlapping calls both diff against the same stale snapshot. This was a real, reproducible bug on Tarefas: checking/unchecking several tasks quickly (no debounce on `quickToggleTask`, by design — the checkbox must move instantly) fired multiple concurrent `syncSheets` calls; the first one's upsert landed and bumped that row's `lastModified` on the sheet, but a second call already in flight had captured the OLD `lastModified` as its `expectedLastModified` for that same row — a guaranteed conflict, which rejects the WHOLE batch (all-or-nothing) including a different row's change that had nothing to do with the stale one. The user saw exactly this: 1 of 5 rapid toggles would persist, the other 4 silently reverted with "Não consegui atualizar a tarefa." Fixed by queuing the actual send (never the optimistic mutation/render, which still happen synchronously and instantly on every call) — by the time a queued call's turn arrives, every earlier one has resolved and updated the snapshot, so the diff naturally reduces to just the genuinely unsaved delta, and rapid taps coalesce into correctly-ordered, non-conflicting requests instead of racing each other. Verified with a throwaway Playwright harness that fires 5 checkbox clicks with zero gap between them and confirms all 5 persist server-side; negative-controlled against the pre-fix code, where the same reproduction left 4 of 5 unsaved. **Reusable pattern:** any client-side diff-against-last-known-state sync mechanism needs its diff+send step serialized (a simple promise-chain FIFO is enough) whenever the UI can plausibly trigger it faster than one round trip — optimistic UI makes rapid-fire input easy to produce by design, and an unserialized diff will eventually diff against its own stale snapshot. **Update — this fixed one of five failure modes, not the whole problem.** Serialization is still required and still in place (`enqueueSync_` now backs both `syncSheets` and the `getAll` apply step), but rapid toggling kept failing afterwards for four independent reasons: whole-array rollback on failure, `renderAll()` re-bucketing the row out from under the next tap, a 23px hit target inside a clickable card, and background hydration clobbering pending changes. See the invariants below; and note that `quickToggleTask` no longer awaits or renders at all — the "no debounce, by design" reasoning in this bullet has been superseded by the pending-mutation model. **Second update — the sixth failure mode, found only once tested against the real backend instead of a stub.** All five fixes above still shipped a live production bug: none of them touched what `sheetSnapshot` gets seeded *from* at boot. See the cache-first-boot invariant below (and "Testing sync/conflict/timing races" in Section 8) for the actual root cause and why the 24-check harness for the five fixes above couldn't have caught it.
- **Conflict detection:** row-level tabs carry a `lastModified` timestamp. A write includes the `expectedLastModified` it last saw; the backend rejects (all-or-nothing per batch) if the current value doesn't match, meaning someone else edited that row in the meantime. **A row that has VANISHED is its own kind of conflict, reported as `{deleted:true}` — never "treat as new".** `findConflicts_` used to fall through on a missing row and let `applyBatch_` re-append it, so a device holding stale state could resurrect a record another device had deleted — and, worse, recreate rows of a project `deleteProject_` had just removed, leaving orphans nothing could resolve or clean up. An `expectedLastModified` is only ever set for a row the client has actually seen the server hold, so "it had one and the row is gone" can only mean deleted-elsewhere. The client (`dropDeletedRows_`) removes those ids from live state, from `sheetSnapshot` and from the payload it retries, and says so out loud rather than discarding the user's edit silently. **Reusable pattern:** in a last-write-wins sync, "absent" and "changed" are different answers; collapsing absent into "create it again" turns every delete into a race the deleter can lose.
- **Notas/Fotos are "computed union" tabs**, not simple 1:1 arrays: they contain both standalone records and records attached to a parent (an entry, a task, or — for a photo — sometimes a note that is itself attached to an entry). Resolving "what project does this row belong to" requires walking that chain (see Data Structure below).
- **Every write is optimistic AND self-healing on failure.** The pattern every write call site follows: clone the state array being changed (`cloneState_`), mutate the live array in place, render immediately, then `await saveKey(key, value, previousValue)`. If the save fails, `saveKey` itself restores the module-level array to `previousValue` before returning — the caller's own (unconditional) `renderAll()` afterward then redraws the real, unsaved state instead of a phantom record that looks saved but never was. This was a real gap for a while: writes mutated state and only skipped the *success* toast on failure, leaving the mutation in place. **Reusable pattern:** any future optimistic-UI write should follow this exact snapshot-then-restore shape, not just suppress the success message. **But see the next bullet for its hard limit** — the whole-array form of this pattern is only safe where no *other* mutation on that same array can be in flight at the same time.
- **INVARIANT — an optimistic mutation must never roll back or replace unrelated state; and background hydration must preserve pending local mutations.** These are two halves of one rule and both were violated in the Tarefas checkbox path, which is what made rapid checking/unchecking fail intermittently:
  - **Whole-array rollback erases other people's work-in-progress — including the same user's.** `saveKey(key, value, previousValue)`'s `previousValue` is a clone taken *before this one mutation*. If a second mutation on the same array happens while the first is still in flight, that clone already predates it, so restoring it on failure silently erases an intention the user watched apply — and which may already have been persisted, leaving memory and sheet permanently divergent until a reload. Symptom: "I check 5 tarefas, 1 sticks and 4 quietly revert." Every task write path now reverts only what it changed (a single task's `feito`, its `fotos` list, its edited fields, or splicing one row back at its original index) and passes no `previousValue`. The whole-array form survives only where concurrent mutation genuinely can't happen; **prefer per-record rollback for anything a user can trigger twice before one round trip completes.**
  - **A cache/hydration is not an authority over unsaved intent.** `fetchAndApplyFromServer()` rebuilt `tasks` wholesale from the server, so a background `getAll` landing mid-burst reverted every still-pending toggle. It now computes `displayed state = server snapshot + pending local mutations`: the fetch stays outside the sync queue (a slow refresh must never delay a save) while the *apply* is queued through `enqueueSync_` so it can't land between a write's request and its response; and `reapplyPendingTaskChanges_()` runs **after** `rebuildSheetSnapshot_()`, so the snapshot holds the server's value (keeping the pending change a genuine unsaved delta) and each pending row's rollback baseline is refreshed to it. Re-applying *before* the rebuild would bake the pending change into the baseline and it would never be sent at all.
- **Rapid taps are independent user intentions, not repeated saves of the whole tab.** `pendingTaskChanges` (a `Map` of task id → `{desired, baseline}`) is the model: `desired` is the current intention, `baseline` the last server-confirmed value that a failure reverts to. Three properties make it correct regardless of tap speed, network timing, failures, hydration, re-renders, or a card opened mid-burst: (1) failures are per-task, per above; (2) **the newest intention always wins** — each flush records the exact `desired` it sent and applies the response to a task only if the user hasn't toggled it again meanwhile, so a late response from an older request can never overwrite a newer local intention; (3) **correctness never depends on the user stopping** — the 120ms flush window is a *leading* window (the first unsaved change starts the clock and nothing pushes it back), not a trailing debounce, and anything still pending when a flush finishes immediately schedules the next. **Reusable pattern:** coalescing/debouncing is a network optimisation layered on top of a correct model, never the mechanism that makes it correct. If the design only works because taps happen to stop, it doesn't work. The existing `syncQueue` FIFO is still required underneath all of this — it's what guarantees `expectedLastModified` is never read from a snapshot an unresolved write is about to change.
- **`renderAll()` must NOT be the immediate response to a checkbox tap (or any rapid-fire control).** A full re-render rebuilds the task DOM *and re-buckets the row into a different container* — checking a task moves it from Em aberto to Concluídas — so the row leaves the moment it's tapped, the next row slides up into the space the finger is already traveling toward, and the following tap lands on a different task or on the card body (opening the detail modal). This, not hit-testing alone, is what made the checkbox feel unreliable. A tap now calls `patchTaskRowClass_(id, feito)`, which toggles the `.done` class on the existing node(s) — covering both the Tarefas page and the Painel widget, since both render `.task-row[data-id]` — and re-bucketing is deferred to a trailing 600ms settle timer (`scheduleTaskSettle_`). 600ms because taps down a list land ~200–350ms apart on a phone: long enough that a burst never reshuffles mid-flight, short enough that one deliberate tap still visibly lands in Concluídas. **Reusable pattern:** for any control a user can hit repeatedly, the immediate response must be an in-place visual patch; anything that reorders, re-buckets, or rebuilds the list belongs on a trailing settle timer, or the UI moves the target out from under the next tap.
- **A touch target must be ≥44px even when the visual affordance is smaller, especially inside a clickable parent.** `.task-check` is a 23px box nested in a fully-clickable `.task-row`, so every near-miss became "open the card." It now carries a 44×44 absolutely-positioned `::before` overlay that contributes nothing to layout; a pseudo-element is never its own hit-test target, so taps inside it resolve to `.task-check`. `position:relative; z-index:1` on `.task-check` is load-bearing — without it the overlay hit-tests *underneath* the in-flow `.task-body` beside it. `touch-action:manipulation` on both removes iOS's 300ms double-tap-zoom delay, which matters a lot when tapping quickly. Handlers keep `stopPropagation()` (keeps the tap out of the row's open-card handler) *and* `preventDefault()` (stops iOS synthesising a second delayed click on the row underneath).
- **Task modal state is navigation state, strictly separate from persistence state.** Opening, closing, or editing a card must not cancel, await, or be cancelled by a pending checkbox mutation, and vice versa. `#toggleTaskBtn` registers the same independent mutation a checkbox tap does and closes the modal immediately rather than awaiting the save; `syncTaskModalToggleLabel_()` keeps an open card's button label honest without touching anything else.
- **INVARIANT — a cache-first boot's in-memory snapshot is UNVERIFIED, and nothing may write against it before that boot's own `getAll` confirms it.** This was a real production outage, not a theoretical risk: the FIFO `syncQueue` (above) prevents two *writes* from racing each other's snapshot reads, but it did nothing to stop a write from racing the boot's own *read*. Sequence: device A checks a task, its write succeeds on the server, but the app is closed before the next cache write (`saveCacheToLocalStorage()` was, at the time, only ever called after a `getAll` — never after a successful write) — so the cache is left holding that task's *pre*-write `lastModified`. Next launch: `loadCacheFromLocalStorage()` seeds `sheetSnapshot` from that stale cache and the app renders immediately (by design — see "time until useful" above); if a checkbox is tapped in the few seconds before the boot's `getAll` lands, the flush diffs against the stale baseline and asserts an `expectedLastModified` the server already moved past. The backend rejects the WHOLE batch (all-or-nothing), including every *other*, perfectly valid task in it — reproduced live as "Não consegui atualizar N tarefas" with every tapped task dumped back into Em aberto. Root-caused and reproduced against the real, unmocked `backend/Code.js` (not a hand-written stub) via a throwaway Node harness that loads `Code.js` into a mocked Apps Script `vm` context exactly like `backend_test.js` does — this mattered: an earlier round of "fix and verify" work had used a hand-rolled `batchMulti` stub whose conflict rule matched the real one but which always seeded `sheetSnapshot` from a real `getAll`, never from a stale cache, so it could not have caught this by construction. **Three-part fix, all required together:**
  1. **A cache-first boot's write path must be gated behind that boot's own `getAll`, not just serialized against other writes.** `hydrateFromServerAtBoot_()` wraps the fetch AND the apply in one function handed to `enqueueSync_`, called synchronously in `loadAll()` before any `await` — so it occupies the front of `syncQueue` for its entire duration, however long the fetch takes, and any write enqueued afterward (a tap a millisecond later) is guaranteed to chain behind it. **This must NOT be done by splitting fetch-outside/apply-inside the way the general-purpose `fetchAndApplyFromServer()` does** (used for manual "Sincronizar agora" and proactive refresh, where the *existing* snapshot is already trustworthy and only the apply needs serializing) — doing that here deadlocks: the apply step wouldn't be enqueued until the fetch resolves, by which time a write's own (earlier, tap-time) `enqueueSync_` call would already occupy the queue ahead of it. **Reusable pattern:** "cache-first render, hydrate in background" always needs an explicit answer to "what happens if a write fires before hydration lands" — the answer can't be "the existing serialization handles it," because serializing writes against each other says nothing about serializing a write against the boot's own unverified read.
  2. **A conflict deserves exactly one retry, rebased against the server's own reported current value — never a silent black hole, never an infinite loop.** `findConflicts_` (`Code.js`) now returns each conflicting row's `currentLastModified` alongside its id (additive — an old, not-yet-redeployed frontend simply ignores the extra field). `rebaseConflictsAgainstServer_()` (`index.html`) writes that value onto `sheetSnapshot` for just the conflicting rows — never touching their other fields, since a full-row upsert already carries the live, current user intent — and `syncSheetsNow_` retries ONCE with the corrected baseline. This can't tell a stale-baseline false conflict (case 1 above — always resolves silently on the first retry, since nothing else is racing it) apart from a genuine concurrent edit by someone else (last-write-wins after one retry, consistent with this app's row-level, no-field-merge conflict model everywhere else) — but it doesn't need to: a SECOND conflict on the same row right after rebasing can only mean real, ongoing contention, so that's exactly when the existing "outros dados foram alterados" message should fire. **Reusable pattern:** don't let "the baseline might be stale" and "someone else might be editing this" collapse into the same one-shot failure — a single rebase-and-retry cheaply resolves the former and still reports the latter, and one retry is enough to tell them apart because the former can never fail twice in a row.
  3. **A successful write must refresh the cache too — but only AFTER patching the live state's `lastModified` with the value the server actually returned, never the client's optimistic guess.** Caching *only* after `getAll` was the direct cause of the stale-cache window in the first place. But naively adding a cache write to `syncSheetsNow_`'s success path would have made things WORSE, not better: `quickToggleTask` stamps a task with a client-side `Date.now()` purely so it sorts correctly in the UI before confirmation — that guess is never what the sheet ends up holding (the backend generates its own `Date.now()`, on a different clock, when it actually writes). Caching that guess would silently reintroduce this exact bug in a smaller window. `applyServerLastModified_()` runs first: ids are generated as `prefix_timestamp_random` and are effectively unique across every sheet, so one flat id→lastModified map (built from the batch response) and a single pass over every state array — including the nested `.notas[]`/`.fotos[]` structures the cross-cutting-sheets model describes — patches every matching live object, wherever it actually lives, with no need to know in advance which sheet or parent an id belongs to. Only then does `saveCacheToLocalStorage()` run. **Reusable pattern:** a cache write is only as correct as the values in the state it serializes — before adding a new place that writes the cache, verify every field being cached is the *authoritative* value, not a client-side placeholder that happens to look plausible on screen; if it isn't, patch the authoritative value back into live state FIRST, in the same success path, before the cache write.
- **Render BEFORE the await, not after it.** "Optimistic" only pays off if the paint happens before the network round-trip, not once it returns. `quickToggleTask` and the Tarefas `#saveTaskBtn` handler mutate state, then `renderAll()` (and, for the add-task form, clear the form and its draft photo thumbs), and only then `await saveKey(...)`. The checkbox moves and the form clears on tap; the round-trip is invisible. On failure the rollback path re-renders *and* restores the form fields and draft photos from the values captured before the mutation, so nothing the user typed is lost — the rollback has to restore the **UI inputs** too, not just the state array, which is the part that's easy to miss. **Reusable pattern:** any write whose result the user is waiting to see should render optimistically first and treat the failure path as a full restore (state + form), rather than awaiting the save to decide what to draw.
- **Double-submit guard:** `withGuard(fn)` wraps an async click/submit handler so a second tap while the first is still in flight is a no-op, not a duplicate write. Applied to every button that creates/edits/deletes a record directly (not to the ones gated behind `showConfirm`/`showPrompt`, which are already idempotent — each resolves its promise exactly once). **Important:** a `<button type="submit">`'s handler must call `e.preventDefault()` *outside* the guard (see the entry form's `submitEntryGuarded` wiring) — if `preventDefault` itself is skipped on the blocked second call, the browser's default submit/navigate action still fires.
- **A file upload is a background lifecycle, never something the UI waits on.** Uploads used to run inline in each file picker's `change` handler — compress → upload → await, one file at a time — with the state mutated and rendered only after the whole loop finished. An 18-photo batch therefore showed nothing at all until every file had round-tripped, behind a *persistent* toast (no timer, replaceable only by the line at the end of the loop). And the freeze had no upper bound: `uploadToDrive` wraps `sheetsPost` = `withRetry(2, 900)` around a 60 s fetch deadline, and the old `processAndSavePhoto` then retried the whole thing once more with heavier compression — ~6 minutes of worst case for ONE file, with the other 17 and the toast frozen behind it. Now the picker does **no network work at all**: it mints records, drops placeholders into the normal state arrays, renders, and returns synchronously; every byte moves afterwards through a background queue (`enqueueUpload_`/`drainUploadQueue_` in `index.html`). Per-file lifecycle: `pending → uploading → saving → done` (record dropped) or `→ failed` (no Drive file; retry re-uploads) / `→ save-failed` (Drive file EXISTS; retry only re-persists). The pieces that make it correct, each load-bearing:
  - **The thumbnail is the progress indicator; the toast only summarises the batch.** The placeholder renders from `URL.createObjectURL(file)` — instant, no compression on the critical path — with a status overlay drawn by `uploadStatusOverlay_`. Compression moved *into* the queue precisely because it is real work (~0.3–0.8 s per phone photo): doing it up front would have put 5–15 s between the picker closing and the first thumbnail. Measured: 18 thumbnails on screen in well under 1.5 s while every upload is still in flight. **Reusable pattern:** when "show it immediately" competes with "process it properly," find the representation that needs zero processing (an object URL, the file's own name) and let the real work happen behind it.
  - **A batch must be structurally incapable of getting stuck, not merely unlikely to.** Three independent mechanisms, all required: every loop iteration is individually `try/catch`ed so one file's exception can never reach the loop; every file carries a hard wall-clock deadline (`UPLOAD_DEADLINE_MS`, 90 s, via `withTimeout`) so a promise that never settles still ends; and the runner's own `finally` always finalizes the progress toast even on an unanticipated throw. There is deliberately **no** batch-level `try/catch` and **no** `Promise.all` — 18 files must not share one fate. Verified by hanging file #3 forever and confirming files 4–18 still complete, the batch terminates, and the toast resolves. **Reusable pattern:** "one item can't block the batch" is a property of the loop's structure (per-iteration catch + per-item deadline + outer finally), never of the items being well-behaved.
  - **A record's permanent id is minted client-side BEFORE the upload starts, and is the only handle used afterwards.** `pendingUploads` is a `Map` keyed by that id; nothing is ever identified by array position. Completion re-resolves where the record actually lives *right now* via `findUploadHome_(id)`, searching the draft arrays and then every owner array — because between enqueue and completion the user may have saved the draft (moving the photo into a real lançamento/tarefa/nota), deleted it, added more, or had the array replaced by a background `getAll`. `findUploadHome_` returning null means "this belongs nowhere any more", which is also what drives cancellation cleanup. **Reusable pattern:** for any async work that completes against mutable UI state, re-resolve the target by stable id at completion time — never capture the array, the index, or even the object reference at enqueue time.
  - **A row with no Drive file must never reach the sheet, and the exclusion must be scoped to in-flight ids specifically.** `persistableFotos_`/`NO_DRIVE_FILE_YET` filter `computeFotosRows()` (and the `documentos` branch of `toSheetRows`) so a placeholder can't be written with a blank `driveFileId` — which would look, to this app and to anyone reading the sheet, exactly like a saved photo. Scoped to ids *this session is still uploading* rather than the broader "driveFileId is blank", because `diffRows_` turns an omitted row into a **DELETE**: a broader predicate would silently delete any pre-existing blank-`driveFileId` row the sheet already holds. `saving`/`save-failed` deliberately DO pass the filter — those already have a real Drive file and are a genuine unsaved delta the next sync should pick up.
  - **The cache must never hold an in-flight upload** (`cacheableState_`). Harmful in both directions: a cached photo with no Drive file yet returns on the next boot as a permanently broken thumbnail with no pending record left to explain or retry it; and — worse — since `loadCacheFromLocalStorage()` seeds `sheetSnapshot` from that same state, a never-persisted row would appear in **both** state and snapshot, so the diff would see no change and the photo would silently never be written at all. Local previews (object URLs) live only in `pendingUploads`, never in the state arrays, the cache, or a sheet row.
  - **Drive-success + metadata-save-failure is its own state, not a generic failure.** `persistUploadedRecord_` leaves the record in state *with* its `driveFileId` and marks it `save-failed` — never rolled back — so the next sync of that sheet picks it up as an ordinary diff, and the thumbnail offers an explicit retry meanwhile; retrying a `save-failed` record re-persists **without** re-uploading (verified: Drive file count unchanged, no duplicate). This is the same reasoning the documents path already used, promoted to an explicit state. What must never happen is a Drive file the app has lost the reference to.
  - **Uploads run with limited concurrency (`UPLOAD_CONCURRENCY = 3`), not one at a time.** This was declined twice before (parallelising used to just move the wait into `LockService` lock contention, since `uploadFile` ran inside the same script lock as every write) — see the backend bullet below for why that's no longer true. `startUploadRunner_` tops up a pool of workers (`runUploadWorker_`) up to the concurrency limit, each independently draining `uploadQueue`; the per-item invariants that make a batch structurally impossible to hang — its own `try/catch`, its own `withTimeout` deadline — are unchanged and now apply **per worker** rather than per sequential iteration, so a hung file only occupies one of three workers until its deadline instead of blocking the whole batch. Relies on JS's run-to-completion semantics: each worker spawned by `startUploadRunner_`'s `while` loop runs synchronously (incrementing `activeUploadWorkers`, shifting its own item off the queue) up to its own first `await`, so the loop's own counters are always accurate by the time it checks them again — no two workers can ever be spawned for the same queued item, and calling `startUploadRunner_` redundantly (every `enqueueUpload_`/`retryUpload_` call does) is a safe no-op once the pool is full. Measured: 9 files at a simulated 500ms/upload each completed in ~1.6s (vs. ~4.5s sequential), confirming true 3-way concurrency via a route handler that counts simultaneous in-flight `uploadFile` requests.
  - **An upload that reached Drive is journaled to `localStorage` BEFORE the row write is attempted** (`saveUploadJournal_`/`resumeJournaledUploads_`). The gap between "the bytes are in Drive" and "the app has a row for them" is where photos went missing: a record whose upload succeeded but whose row write failed lived only in memory, stayed on screen with a retry affordance, and survived **only** if some later unrelated write to the same tab happened to sweep it up — because `saveKey('tasks')` sends the whole recomputed Fotos diff, so any checkbox tap would do it. Reproduced both ways: with another write following, the photo persisted; with nothing following, a reload lost it and orphaned its Drive file. That is the "photos disappear, then reappear when I start another upload" behaviour, and it is why it felt impossible to know what state a photo was in — the answer genuinely depended on unrelated activity. The journal stores metadata only, never bytes: by that point the expensive part is done and all that remains is writing a row, so the next boot finishes the job rather than losing it. **Reusable pattern:** whenever a multi-step operation has an irreversible middle step (bytes uploaded, payment taken, message sent), the fact that it happened must be recorded durably *before* the remaining steps are attempted — otherwise the only record of it is in memory, and its survival depends on luck.
  - **Draft photos survive navigation.** Leaving Tarefas or Notas used to destroy any draft photos on those forms — cancelling their uploads and discarding the files — so photos picked seconds earlier vanished because the user glanced at another tab. Tapping a tab is not a "discard my work" gesture; drafts are cleared when the form is actually submitted or explicitly reset, exactly as the Add form's already were.
  - **The upload journal is session state, not device state, and a job that can never succeed must be discardable.** It survived sign-out, so the next person on a shared device resumed the previous user's photo job under their own token; sign-out now cancels in-flight uploads and clears `UPLOAD_JOURNAL_KEY` alongside the data cache. Worse, a resumed job whose parent record had since been deleted fell through to a full re-upload with no `File` (the journal stores metadata only — by then the bytes are already in Drive), threw inside `compressImageFile(null)`, and re-journaled itself: it came back and failed again on EVERY launch, forever, and the tray's "Descartar" explicitly refused to remove it because it already had a `driveFileId`. `runOneUpload_` now drops such a job outright (its Drive file is exactly what `sweepOrphanFiles` reclaims), and an explicit discard can force-remove a `save-failed` job. **Reusable pattern:** protecting a record from accidental deletion is right up until the record can no longer make progress — every "we must not lose this" guard needs a deliberate escape hatch, or it becomes a state the user cannot leave.
  - **Known limitation:** a draft form genuinely abandoned (never submitted) leaves its already-uploaded Drive files with no row. Those are reclaimed by `sweepOrphanFiles()` (Section 7), not from the client — the server resolves a file's permissions from its row, and deliberately refuses a bare `fileId`.
- **A bulk operation must never be expressed as N individual row writes through `batchMulti`.** Project rename used to rewrite every referencing row's `projeto` field and send it as a `batchMulti` of one upsert per row — fine at small scale, but for a project with real history this could exceed Apps Script's execution time limit and fail with only some rows renamed, orphaning the rest. It's now a dedicated backend action (`renameProject_` in `Code.js`) that bulk-rewrites each sheet's `projeto` column with one read + one write per sheet, regardless of row count, inside the same script lock as every other write. **Reusable pattern:** any future "rename/retag many rows at once" feature should get its own dedicated bulk action the same way — never a loop that emits one `batchMulti` upsert per affected row. **`renameProject` is gated on `config`.edit AND, independently, `hasProjectAccess_`** — it was missing the second axis for a while, which meant a project-scoped user whose role carried `config.edit` could rename a project they could not even see, bulk-rewriting the `projeto` column across five sheets outside their scope. Every write action checks both axes; there are no exceptions, and "this action only edits one cell" is not one (this one cascades).
- **Deleting a project (`deleteProject_`) is the same bulk shape as rename, plus a resolution-order rule.** It removes every CaixaObra/Empreiteiro/Tarefas/Documentos row for the project, the Notas and Fotos rows that resolve to it, the Projetos row itself, and trashes the project's Drive folder — one read + one write per sheet (`deleteProjectRowsBulk_`), never `deleteRowsByIds_` (which calls `deleteRow()` once per row: fine for a handful of ids, fatal for a project owning thousands). **Order is load-bearing in TWO separate places**, and both are the same "a parent-deletion cascade must delete the children FIRST" rule the single-record delete path already follows, applied one level up. Notas/Fotos carry no project of their own and resolve it by walking up to their parent entry/task/note, so: (a) *resolution* must be computed while those parents still exist — hence the single up-front read pass before anything is written; and (b) *deletion* must ALSO run children-before-parents. (b) is the non-obvious half and was a real defect found by a post-ship audit, not by any of the 52 passing tests written for this feature. **Nothing here is transactional** — Sheets has no rollback, so a failure between two writes (a Sheets error, or the 6-minute execution limit, likeliest on exactly the large projects this bulk path exists for) leaves the operation half-done and the user's only recovery is to run it again. With parents deleted first, that retry **could not finish**: the second run's `entryIdx` no longer contains the deleted parents, so `resolveFotoProject_`/`resolveNotaProject_` return `undefined` and those child rows never match the project again — permanently stranded, and invisible to `sweepOrphanFiles` too, since it iterates `readSheet_('projetos')` and the project is gone. Doing children first costs nothing (resolution already happened) and makes every failure point recoverable. Verified by failing each of the six write steps in turn and retrying: 5 of the 6 stranded orphans before the fix, 0 after. The Projetos row still goes last, so a partial failure leaves a project that visibly still exists (and can simply be deleted again) rather than orphaned rows pointing at a project that doesn't. **Reusable pattern:** for any multi-step destructive cascade over a store with no transactions, "what does a retry see?" is a separate question from "is the happy path correct?" — order the steps so that every prefix of them leaves the remaining work still *derivable*, which for parent/child data means deleting in child-to-parent order even though resolution runs parent-first. **Ids are backfilled (`backfillMissingIds_`) before anything is resolved**, because `readSheet_` mints a FRESH random id for a blank-id row on every call — so the doomed-id set built from the first read never matched the ids the second read (inside `deleteProjectRowsBulk_`) invented, and a hand-typed Fotos/Notas row was reported as deleted while silently surviving, pointing at a Drive file that had just been trashed with the folder. **Drive is trashed by FOLDER, not per file** — one call takes everything inside, deliberately avoiding the unbounded-cost-per-id shape that `DELETE_CHUNK_SIZE` exists to work around; a stray file outside the folder has no row any more, so `sweepOrphanFiles` reclaims it. Gated on `config`.**delete** (not `config`.edit — a role trusted to add and rename projects is not automatically trusted to destroy one) *and*, independently, `hasProjectAccess_`.
- **`writeSheet_` must DELETE surplus rows, not just `clearContent()` them — a leftover blank row is not inert.** Whole-tab replace used to clear the old data range and write the new rows over it, leaving the physical rows behind when the new list was shorter. That looks harmless and isn't: `readSheet_` maps a blank row into an object and mints an id for it, then `backfillMissingIds_` (top of every `getAll`, under the lock) writes that generated id back to the sheet — promoting a leftover blank into a **permanent phantom record with a real id**, surfacing in the app as an empty lançamento/tarefa nobody created. It stayed invisible only because no caller had ever meaningfully shrunk a sheet; it was already latent for `saveProjetos_` and for removing a Tipo/Unidade, and `deleteProject_` would have hit it on every single delete. Verified by reproducing it against the shipped `Code.js` through the existing `saveSheet` path alone (3 projects → 1 left two blank rows), independent of the new action. **Reusable pattern:** when a "replace everything" write can produce a *shorter* result than what's there, clearing values is not the same as removing rows — and check what the read path does with the empty remainder before assuming it's harmless, especially if any repair/backfill pass will later treat it as real data worth completing.
- **`writeSheet_` must carry any manually-added column ALONG WITH its row, not leave it behind.** A whole-tab replace rewrites rows positionally but only across the schema's own columns, so a column someone added by hand to the right of the schema kept its original row position while the data above it shifted up — silently re-attaching every manual note to the wrong record, with no error and nothing on screen to reveal it. Harmless while this only ever touched Projetos/Tipos/Unidades; a live data-corruption path the moment `deleteProject_` started using it on the six row-level sheets. It now reads the sheet's full width, keys the extra cells by column A (the id for id-bearing sheets, the value itself for the single-column reference lists) and re-emits them next to their own row; a genuinely new row gets blanks. **Reusable pattern:** a positional bulk write is only safe if it owns every column it shifts — if the sheet is a place humans also work, assume they have added a column and make the write carry it.

### Important architectural decisions already made
- `window.storage` (an earlier, Claude-artifact-specific storage mechanism) was **fully removed** early in this project's history in favor of the Sheets/Drive backend — this was a deliberate migration, not leftover cruft to "clean up."
- IndexedDB was tried and **rejected** for photo storage (blocked by desktop browsers' third-party-iframe storage restrictions in some contexts) in favor of routing photo/doc blobs through the same `window.storage`-style mechanism, which was itself later superseded by Drive upload once the Sheets/Drive backend was built.
- A shared-secret query-param scheme (`SHARED_SECRET`) was the **original** auth mechanism and has been **fully replaced** by real Google Sign-In + backend token verification. No trace of it should remain in either file.

## 4. Authentication & Permissions

### How users are authenticated
- Google Identity Services issues a signed ID token client-side after Sign-In/One-Tap.
- The token is sent with **every** request (`idToken` param) and is **verified independently by the backend on every single request** via `verifyIdToken_()`, which calls Google's `tokeninfo` endpoint and checks: token validity, `aud` matches `GOOGLE_CLIENT_ID`, and `email_verified`.
- The verified email is then looked up in the `Usuarios` sheet by `getCurrentUser_()`. Unknown or deactivated (`ativo` ≠ SIM) users are rejected.
- **Critical established principle:** hiding UI elements is a courtesy only. All real enforcement happens server-side, on every `doGet`/`doPost`, independent of what the frontend shows or hides.

### Session/token storage rules (established, must not be violated)
- The raw Google ID token is held **only in an in-memory JS variable** (`googleIdToken`), never written to `localStorage` or any persistent storage.
- A lightweight **session hint** (`cmoreira_session_hint` in `localStorage`) stores only `{email, timestamp}` — never the token. It is a UI hint only ("should I attempt a silent restore on load?"), never treated as proof of authentication. Real access always requires the backend to independently re-verify a fresh token.

### Roles, sections, and actions (established — page/section/action permission model)
Permissions are no longer hardcoded per role in `Code.js`. Instead, `Code.js` defines the *shape* of the model and a **`Papeis` tab** (in the same `Usuarios` spreadsheet) holds the actual role capabilities as data.

**⚠️ MAINTENANCE RULE — read before touching any permission-related code or UI:** the tables below (this subsection and "Current permission map") are the authoritative, must-stay-accurate description of every page, every subsection, and what governs each. Whenever a change adds/removes a page, a subsection, a cross-cutting data type, or changes which section governs something, **update these tables and the `installPapeisSheet()` seed in the same piece of work** — not as a follow-up. A stale map here is worse than no map.

**Page vs. section — these are NOT the same thing**, even though for most of this app they coincide 1:1:
- A **section** is the actual unit of permission — `SECTIONS` in `Code.js` maps each one to the business-data sheet(s) it owns outright: `painel` (none), `lancamentos` (CaixaObra, Empreiteiro), `tarefas` (Tarefas), `notas` (none — see "Cross-cutting sheets" below), `docs` (Documentos only), `config` (Projetos/Tipos/Unidades), `usuarios` (none, reserved).
- A **page** is a nav tab. Most pages are backed by exactly one section of the same name. The one exception: **`painel` embeds a widget summarizing Tarefas data**, and that widget has its OWN section, `painel.tarefas` (a dotted `page.subsection` key) — independent from both `painel` (is the dashboard reachable) and `tarefas` (is Tarefas data/page viewable at all). A role can have either without the other. The widget can never show more than `tarefas`.view already allows; the dotted key only additionally hides an already-authorized widget. **Reusable pattern:** a future dashboard widget for another section is just another `painel.X` key — no new mechanism, no code branch.
- **Action** — `view | create | edit | delete | upload | export`, defined once in `PERMISSION_ACTIONS`. **`export` is currently declared but never checked anywhere** — there is no export feature yet. It stays in the list and in the seed so the matrix has a stable shape, but do not read a `SIM` in that column as evidence that anything enforces it; wire a real check at the same time you build the feature. Every section gets all six columns even where most are meaningless for it (e.g. `painel` only ever uses `view`) — deliberately uniform, so nothing special-cases a section's allowed action set.
- **Papeis tab** — columns `role | section | view | create | edit | delete | upload | export` (`SIM`/`NAO`). A `(role, section)` pair with **no row** means every action on that section is denied — deny-by-default falls out of the data itself, not an `if` naming a role or section. There is deliberately **no wildcard row** (e.g. `role | * | ...`) — every role gets one explicit row per section it has any access to, so a brand-new section never gets accidentally auto-granted to an existing role. Run `installPapeisSheet()` once (Apps Script editor, function dropdown) to create and seed this tab; it won't overwrite a tab that already has content, so it's safe to re-run. **Function naming note:** manually-run setup functions in this file must NOT end in a trailing underscore — Apps Script's editor hides any such function from the "Select function" run dropdown (its own convention for "private helper"), which is exactly why `installPapeisSheet`/`flushPermissionCache` don't have one, unlike every other helper in the Authorization block.
- **Sheet completeness vs. code behavior — two different things, on purpose.** `installPapeisSheet()`'s seed writes every `(role, section)` combination this app knows about, including denied ones, as explicit `SIM`/`NAO` — never a blank cell — purely so a human can read the sheet top to bottom and see exactly what every role can do, without having to know "no row here means denied" as an unwritten rule. This is a **presentation choice, not the security boundary**: the backend (`buildPermissionMatrixFromSheet_`/`sectionsForRole_`/`can_`) must keep treating a missing row, a blank cell, an unrecognized role or section, or a missing `Papeis` tab entirely as denied, regardless of whether the sheet is currently complete. If you ever add a role or section and the sheet temporarily has gaps (mid-edit, a row deleted by accident), those gaps must still fail closed on their own — never make the code assume the sheet is exhaustive, and never take "the matrix looks complete" as a reason to loosen a fail-closed check.
- `sectionsForRole_(role)` resolves a role into an explicit `{section: {action: bool}}` object (every known section/action gets a real `true`/`false`, never an implied default) — attached to the user as `user.sections` in `doPost`, right after `getCurrentUser_()`, **not** inside it (see below). `can_(user, section, action)` is the one generic check every enforcement point uses; no role or section name is ever compared by name in code.
- Role names are lowercase internally; the sheet value is lowercased/trimmed on read, so casing in the sheet (`Partner`, `partner`, `PARTNER`) should not matter.

### Cross-cutting sheets: Notas and Fotos (established, non-obvious — read before touching either)
Unlike every other sheet, a single **Notas** or **Fotos** row does not belong to one fixed section — it belongs to whichever section owns its actual parent, and both sheets are rendered **embedded on multiple pages simultaneously**: a task's photo shows inside Tarefas *and* in the Docs gallery; an entry's note shows inside the Lançamentos detail modal *and* in the standalone Notas feed. A blanket "this whole sheet is section X" flag cannot express or enforce that — a role denied `tarefas` but granted `docs` would still receive task-photo rows if Fotos were blanket-owned by `docs` (this was a real gap in an earlier version of this model, closed by the per-row design below).

So both sheets are filtered/authorized **per row**, both for reads and writes:
- `resolveNotaSection_(nota)` / `resolveFotoSection_(foto, notaSectionById)` in `Code.js` (mirroring the existing `resolveNotaProject_`/`resolveFotoProject_` project-resolution chain) return the section that actually owns a row's parent:
  - Standalone note (no `refTipo`, has `projeto`) → `notas`.
  - Note or photo attached to a Lançamento entry (`refTipo` = `caixa`/`emp`) → `lancamentos`.
  - Photo attached to a task (`refTipo` = `tasks`) → `tarefas`.
  - Photo attached to a note (`refTipo` = `notes`) → a 2-hop lookup: whatever section *that note itself* resolves to (`notas` if standalone, `lancamentos` if it's attached to an entry).
  - Photo added directly to a project, with no lançamento/tarefa/nota parent at all (`refTipo` = `projeto`, `refId` = the project's own name — `Projetos.id` doubling as its display name, same key used everywhere else) → `docs`, the same section Documentos already lives under. This is the "Fotos do projeto" album on the Docs page — see Section 6/frontend below. `resolveFotoProject_`'s `projeto` branch is the one case where `refId` itself already *is* the project name, not something to look up in `entryIdx`.
- `filterAllByAccess_()` filters `data.notas`/`data.fotos` row-by-row against `resolveNotaSection_`/`resolveFotoSection_` **before** the generic per-section sheet wipe runs, using project/section indexes built from the **original, unfiltered** read (never from arrays some earlier step already trimmed).
- `assertBatchAccess_()` resolves the section the same way for writes — `sectionForOp_()` special-cases `notas`/`fotos` sheets to call the resolvers instead of the normal `SHEET_TO_SECTION` lookup every other sheet uses.
- `uploadFile` cannot know a row's true parent yet (the Fotos/Documentos row doesn't exist until the follow-up `batchMulti` attaches it) — the frontend sends a `section` hint so a denied role can be stopped before writing to Drive at all, but this is *not* the real security boundary: the subsequent `batchMulti` independently re-resolves the row's actual section from its own `refTipo` and would reject it regardless of what `uploadFile` was told. `deleteFile`, by contrast, has a real existing row to resolve from — it is **fully server-resolved**, no client input trusted at all, same principle as create-vs-edit.
- **Reusable pattern:** if a future data type is similarly embedded across multiple pages, resolve its section per row the same way — never add it to a single section's blanket sheet list.
- **A project rename must also rewrite Fotos rows that carry the project name in `refId` instead of a `projeto` column.** `renameProject_`'s bulk rewrite (`renameProjectColumnBulk_`) only touches sheets that have an actual `projeto` column — Fotos doesn't, since a Fotos row's project is always resolved through its parent. That's fine for every other `refTipo`, but a `refTipo:'projeto'` row's "parent" IS the project name itself, sitting in `refId` — so it needed its own bulk pass, `renameProjectFotoRefsBulk_`, filtering strictly on `refTipo === 'projeto'` (never touching `caixa`/`emp`/`tasks`/`notes` rows, whose `refId` is an entry/task/note id, never a project name). Skipping this would have silently orphaned every project-level photo on the next rename. **Reusable pattern:** whenever a new cross-cutting row type stores a foreign key somewhere other than a column named after that key (here: the project name living in `refId` instead of `projeto`), audit every bulk rename/rewrite path for that key type — a generic "does this sheet have a `projeto` column" check will silently skip it.

### Authentication vs. authorization are two separate blocks, on purpose
`getCurrentUser_()` (AUTH BLOCK) returns identity only — `{email, nome, role, projects}` — read live from `Usuarios` on every request, never cached. It has no idea what a role is allowed to do. `user.sections = sectionsForRole_(user.role)` (AUTHORIZATION BLOCK) is attached separately in `doPost()`. Keep this split if either block is touched again: authentication must never depend on authorization, and vice versa.

### Where users/roles are stored
Separate `Usuarios` spreadsheet (not the business-data spreadsheet):
- **`Usuarios` tab** — identity/eligibility only: `email | nome | role | projetos | ativo | criadoEm`. `projetos`: `*` (all projects) or a comma-separated list of exact project names. **`projetos` is a foreign key BY NAME, in a different spreadsheet from the data it points at, and `renameProject_`/`deleteProject_` are responsible for keeping it in step** (`renameProjectInUsuarios_`/`removeProjectFromUsuarios_`). Nothing did, for a while: renaming a project silently revoked every scoped user's access to it — their `getAll` went to zero projects and zero rows, with no error anywhere and no way for a non-technical user to understand or fix it. Both helpers run FIRST, before any business-data write, deliberately: a failure there is then a clean no-op, and a retry after a partial failure downstream is idempotent (nothing matches the old name any more). `*` is never rewritten, and matching is exact — the same comparison `hasProjectAccess_` itself uses, because a looser match here would grant access the real check would refuse. **Reusable pattern:** a foreign key stored as a display name needs an explicit owner for every rename/delete path; "the other system will notice" is never true when the two systems are separate files. Deliberately has **no** permission columns — those live in `Papeis` instead, so a permission change is a `Papeis` edit, never a `Usuarios` schema change.
- **`Papeis` tab** — role capabilities, see above.
- `user.sections` is *derived* server-side and sent to the frontend as part of the user object on every `getAll`. The frontend never re-implements role→permission logic; it only renders what the backend says (`currentUser.sections`).

### How section/action permissions are determined and cached
- `filterAllByAccess_()` wipes a section's sheets to empty arrays in the `getAll` response when the user lacks `view` on that section — runs generically over `SECTIONS`, no section name special-cased. (Notas/Fotos are handled separately, per row — see above.)
- `assertBatchAccess_()` rejects a write when an op's section+action isn't permitted, independently of the existing project-scope check, checked server-side regardless of what the frontend UI shows.
- **create vs. edit is resolved from the sheet's own current state** (does this row id already exist?), **never from anything the client claims** — a client mislabeling an edit as a create (or vice versa) cannot use that to dodge a per-action restriction.
- **Established, non-obvious rule:** section/action access and project access are **independent axes**. The section/action check must run unconditionally, even for a user with unrestricted (`'*'`) project access — an early-return for `projects === '*'` must never skip it. (Originally caught as a page-vs-project bug; the same rule now also covers action vs. project — re-verify if this logic is ever touched again.)
- **Permission matrix caching:** `loadPermissionMatrix_()` caches the *role→section→action shape* (from `Papeis`) via `CacheService`, TTL 300s — this is safe because that shape is identical for every user sharing a role. **Never cache a specific user's resolved permissions or identity** — `getCurrentUser_()` stays uncached so a role/`ativo` change on one user takes effect on their very next request. Any cache/read failure falls back to an **empty matrix — fail closed**, not open. Run `flushPermissionCache()` after hand-editing `Papeis` if you don't want to wait out the TTL.
- Frontend: nav buttons are hidden based on `currentUser.sections[section].view` (via a `VIEW_ACCESS` map of view name → `{section, actions}`, supporting an "any of these actions" check — needed because the Lançamentos "add" tab requires `create` OR `edit`, since the same form serves both), **and** `switchView()` itself refuses to activate a disallowed page. Write-affordances within a page (add/edit/delete buttons, photo/document upload inputs, per-item note/photo edit-delete controls) are likewise hidden via a generic `canSection(section, action)` helper (`applySectionUIAccess()` for static elements; inline checks inside render functions for dynamically-generated lists like the Notas feed or Docs gallery, since each row/category can have a different owning section) — reusing the same pages/components, never a role-specific duplicate view. All of this is still just a courtesy; the backend is the real authority.
- **Reusable pattern for future apps on this stack — adding a new permission-controlled section.** No existing role's code path needs to change for any of this; it's purely additive:
  1. **Add it to the server-side section registry** — `SECTIONS` in `Code.js` (plus `VIEW_FILTERED_SECTIONS` if it should gate a nav page's data). This is the actual security boundary: a section absent from `SECTIONS` can never carry real sheet data no matter what `Papeis` says — a `Papeis` row for a section name not in `SECTIONS` is silently never even parsed into `user.sections`, confirmed by direct test (see "Testing permission changes" in Section 8).
  2. **Add an explicit `SIM`/`NAO` row in the `installPapeisSheet()` seed for every defined role** — not just the ones being granted access. Deny-by-default already covers a missing row on its own, but the seed's whole point is a complete, no-guessing picture (see the sheet-completeness rule above) — an incomplete seed for a new section defeats that purpose even though it stays secure.
  3. **Update the "Current permission map" table and this section's description** — and, if it's a page, a `VIEW_ACCESS` entry on the frontend; if it's a dashboard-style widget rather than a full page, a `painel.X`-style dotted key instead.
  4. **Before considering it done, run a focused authorization test with at least one role denied the new section** — confirm its data cannot be reached via the UI, a direct `getAll`/`batchMulti` request, or any embedded/cross-page path it might be reachable through (see "Testing permission changes" in Section 8).
  5. **Missing or invalid configuration must keep failing closed** — no `Papeis` row, an unrecognized role, an unreadable `Papeis` tab. The code already guarantees this; a new section's rollout must never depend on loosening it or on the sheet being complete.

### Session behavior (iOS/PWA-specific, established through direct investigation)
- **Home-screen PWA (standalone mode) cannot silently restore a session on a fresh launch.** A standalone PWA runs in a WKWebView with a storage partition fully separate from Safari — there is no shared Google session for `google.accounts.id.prompt()` to find, regardless of how recently the user signed in within the PWA previously. This is a confirmed platform limitation, not a bug, and is not fixable via GIS configuration.
- The app detects standalone mode (`display-mode: standalone` / `navigator.standalone`) and **skips** the silent-restore attempt there entirely — showing the sign-in button immediately rather than a "Restaurando sessão..." message that could never succeed.
- In a regular (non-standalone) browser tab, silent restore via `prompt()` **is** attempted when a fresh session hint exists, since that context can share a real Google session.
- **Proactive token refresh on foreground return:** a `visibilitychange` listener checks token age when the app becomes visible again; if older than 45 minutes (Google ID tokens last ~1 hour, not app-configurable), it attempts a silent `prompt()` before the user's next action would otherwise fail. Whether this reliably succeeds in practice on real iOS depends on live Google session state that could not be verified from a sandboxed environment — this should be treated as "implemented and reasoned through" but **not** as "confirmed working end-to-end on device."
- `google.accounts.id.prompt()` should never be called unconditionally on every load — doing so previously caused an unwanted One Tap popup for every visitor, including first-time users with no session to restore. It should only be called when there's a specific reason to believe a restore might succeed.

### Formerly-open issue: role change not taking visible effect (superseded)
A user once changed their `Usuarios` row `role` to `Partner` and refreshed, but the app still showed all pages/tabs; the investigation was never fully completed on the old `ROLES`/`pages` model. That entire model (`ROLES` object, `currentUser.pages`, `PAGE_SHEETS`) has since been replaced by the section/action permission model in Section 4 (`Papeis` tab, `currentUser.sections`, `SECTIONS`) — so the specific code paths named in the old investigation no longer exist. If a similar symptom (role change not taking effect) recurs under the new model, first check: the deployed Apps Script is genuinely running the latest `Code.js` (see Section 7 — this project has a strong recurring history of bugs traced back to an edit being saved but not deployed as a "new version"); then whether `Papeis` actually has a row for that role+section; then the `flushPermissionCache()` / 5-minute TTL on the (role-shape-only, never per-user) permission cache — note `getCurrentUser_()` itself is never cached, so this narrows to the `Papeis` matrix specifically.

## 5. Data Structure

### Business data spreadsheet (tabs and key columns)
- **Projetos:** `id, ativo` — `id` **is** the project's display name (e.g., "Obra Gavião"), used directly as the foreign key everywhere else. Renaming a project requires cascading the update to every referencing row (already implemented).
- **CaixaObra:** `id, projeto, data, nome, tipo, qtd, unidade, valor, fornecedor, socio, criadoEm, lastModified`
- **Empreiteiro:** same shape as CaixaObra, minus `tipo`.
- **Tarefas:** `id, projeto, texto, prazo, prioridade, feito, criadoEm, lastModified`
- **Notas:** `id, projeto, texto, criadoEm, refTipo, refId, lastModified` — a **union** of standalone notes (`projeto` filled, `refTipo`/`refId` blank) and notes attached to an entry (`refTipo` = `caixa`/`emp`, `refId` = the entry's id, `projeto` blank/implied).
- **Fotos:** `id, refTipo, refId, driveFileId, driveUrl, criadoEm, lastModified` — `refTipo` can be `caixa`, `emp`, `tasks`, or `notes` (a photo can be attached to a note, which may itself be attached to an entry — a two-hop chain).
- **Documentos:** `id, projeto, nome, mimeType, driveFileId, driveUrl, criadoEm, lastModified`
- **Tipos:** `tipo` (single column, expense category reference list).
- **Unidades:** `unidade` (single column, unit-of-measure reference list).

### Row-level vs. whole-tab tabs
- **Row-level (support upsert/delete + `lastModified` conflict detection):** CaixaObra, Empreiteiro, Tarefas, Notas, Fotos, Documentos.
- **Whole-tab replace (simpler, no conflict tracking — small reference lists, rarely concurrently edited):** Projetos, Tipos, Unidades.

### Auth spreadsheet
Separate spreadsheet, two tabs — see Section 4:
- **Usuarios**: `email, nome, role, projetos, ativo, criadoEm`.
- **Papeis**: `role, section, view, create, edit, delete, upload, export` — role capability matrix.

### Relationships worth knowing
- Determining which project a Nota or Foto belongs to requires resolving through `refTipo`/`refId`, potentially two hops deep (photo → note → entry). This logic lives in `buildEntryProjectIndex_`, `resolveNotaProject_`, `resolveFotoProject_` in `Code.js` and is duplicated conceptually (not literally) on the frontend for local state reconstruction after a `getAll` fetch.

## 6. Frontend/UI Rules

- **Mobile-first, iPhone home-screen PWA is the primary target.** Desktop browser support matters but is secondary.
- **Fixed header pattern:** the topbar is `position:fixed` (not `sticky`) specifically to prevent iOS's rubber-band overscroll from revealing a gap above it; the page background is dark (matching the header) as a fallback in case any edge case still exposes space. Content below is offset by a JS-measured header height (`ResizeObserver`), not a hardcoded padding value.
- **Date fields** use a "fake formatted display + invisible native `<input type=date>`" pattern (for custom `dd/mm/aaaa` formatting). On desktop browsers, the invisible native calendar icon must be triggered via `showPicker()` on click — tapping alone only works natively on iOS.
- **Empty states have no icon** — a "+" icon was previously used and removed because it visually read as a tappable button when it wasn't one.
- **Sort default for Lançamentos is most-recent-first**, using the underlying Google Sheet's row order as the tiebreaker (not `criadoEm`) — `criadoEm` is not a meaningful signal for rows typed directly into the sheet by hand, since they can all get stamped with nearly the same value on first read.
- **Multi-file selection is supported** on all photo/document upload inputs (8 total across the app, after project photos were added) — each renders its files immediately and uploads them in the background (see the upload-lifecycle bullet in Section 3), with per-file state on the thumbnail and batch progress in the global activity hub (see below).
- **The Notas page is a bottom-anchored timeline with a docked composer — three things about it are load-bearing.** The "Nova nota" form-card at the top was replaced by a chat-style composer bar (photo icon button + auto-growing pill textarea + round send button) fixed above the tab bar. Same `#noteInput`/`#notePhotoInputNew`/`#saveNoteBtn` elements and handlers, same optimistic save path, same per-item permission resolution — only the layout changed.
  - **A `position:fixed` child cannot survive a transformed or animated ancestor, and the symptom looks like a scroll bug, not a CSS one.** `.view`'s entry animation animates `transform`, and any transformed ancestor becomes the containing block for a fixed descendant — so on every entry to Notas the composer was laid out relative to `#view-notes` and visibly slid down from the top to its real place. Fixed with `#view-notes{animation:none;}`; verified by sampling the composer's `getBoundingClientRect().top` over 12 frames on entry (pinned at 621px after, drifting 500→494 with `animationName:'fade'` before, against the previous commit served from a second directory). **Reusable pattern:** when a fixed element animates, drifts or lands in the wrong place on view entry, check the ancestors for a `transform`/`filter`/`will-change` before touching the fixed element's own coordinates — either the ancestor loses the transform or the child has to move out of it.
  - **Both of the composer's offsets are MEASURED, never hardcoded**, because both grow at runtime: the tab bar with the safe-area inset, the composer with the textarea and with draft photo thumbnails. `syncNoteComposer_()` publishes the tab-bar height as a `--tabbar-h` custom property (deliberately not an inline `bottom`, which a class could never override — see the composing rule below) and sets `#notesFeed`'s `padding-bottom` from the composer's own height. Driven by a `ResizeObserver` on the tab bar, `resize`/`orientationchange`, `visualViewport` resize (iOS resizes the visual viewport for the keyboard without firing a window resize), and re-run from `renderNotesFeed()` and `renderNoteFormPhotoThumbs()`. The textarea stays at `--fs-title`, since the ≥16px iOS no-zoom rule applies to it like any other input.
  - **The feed has ONE ordering rule — ascending by a normalized timestamp — and nothing downstream reverses it.** `items` sorts oldest→newest and the render walks it in plain array order, so the array order *is* the on-screen order; a page is the N most recent notes, which in an ascending array is the TAIL (`firstIdx = length - visibleCount`), and "carregar mais" therefore sits at the TOP. **The reversal this replaced was a real production bug.** `criadoEm` is *not* guaranteed to be a number: a Notas cell someone formatted as a date comes back as an ISO string (the same latent Sheets corruption `fmtDate_`/`coerceTimestamp_` guard elsewhere — `coerceTimestamp_` unwraps a `Date` object but passes a date-shaped *string* straight through), so `b.criadoEm - a.criadoEm` evaluated to NaN for every pair, the comparator became a no-op, and the array kept sheet-insertion order (oldest→newest). Sorting looked fine; the *reversal* then rendered newest-first — the user's "my note posts at the top" — while identical code with numeric timestamps behaved correctly, which is why it survived a round of testing. `noteTs_()` normalizes number / `Date` / numeric string / ISO string / blank to one comparable number, and a `seq` tiebreak keeps notes that share a timestamp (routine — a blank `criadoEm` is read as `Date.now()`, stamping many rows with the same millisecond) from swapping places between renders. `notesThreadHTML`'s thread sort carries the same normalization for the same reason. Reproduced and negative-controlled with three `criadoEm` shapes (numeric / ISO-string / all-equal) driven through the real UI: the ISO case rendered exactly newest-first on the previous commit and correctly after. **Reusable pattern:** a sort key read from a spreadsheet is untyped input — normalize it at the boundary, because a NaN comparator does not throw or warn, it silently returns insertion order, and any code that then *reverses* that array turns a dormant bug into a visible one.
  - **Two scroll consequences of being bottom-anchored, both required:** entering the page and posting a note jump to the *bottom* (via a one-shot `notesScrollToBottom_` flag, set only by those two moments and consumed by the next render — a background sync or a photo-status patch must never yank someone who has scrolled up); and load-more re-anchors on distance from the bottom, since prepending older notes above the viewport would otherwise shove the reader down the page by the height of everything inserted.
  - **Posting is optimistic: the note is painted BEFORE the save is awaited, and the double-submit guard is deliberately gone.** `#saveNoteBtn`'s handler used to push the note into state and then `await saveKey(...)` before rendering anything at all, so tapping send produced no note and no cleared field until Apps Script answered — measured at **1518ms to visible against a 1500ms backend, versus 4ms after** (negative-controlled against the previous commit). This is the app-wide "render before the await" rule (see the Data flow section) that the entry and task add forms already followed; the composer simply never did, and a messaging-style UI makes the omission feel like a broken tap rather than a slow save. Three things make the optimistic version safe: rollback removes **that one note by id** and `saveKey` is called with **no `previousValue`** (a whole-array clone predates any other note posted while this save is in flight — the same invariant the task form and the checkbox path follow); the failure path restores the **composer text and draft photos**, not just the state array; and the post paints `renderNotesFeed()` only, with the full `renderAll()` deferred and coalesced behind a 400ms timer, since a new note changes no other page except (via its photos) the Docs album. **`withGuard` was removed from this handler specifically**: the composer is cleared synchronously, so a double-tap now hits the empty-text return on its own, and the guard's only remaining effect was to make a genuine SECOND note a silent no-op for the length of a round trip — reproduced, with the third of three quick notes never posted or persisted at all. Concurrent saves were already safe without it: `syncSheets` is serialized through the `syncQueue` FIFO, so the second call diffs against a snapshot the first has already updated. **Reusable pattern:** a double-submit guard protects against a *repeated* submission, not a *rapid* one — once the optimistic render clears the input, the guard stops preventing duplicates and starts swallowing intentions.

When the timer *does* fire, the subsequent `touchend` still produces a normal browser-synthesized `click` shortly after — swallowing it requires a **capture-phase** listener on `#notesFeed` (capture visits ancestors before the target's own bubble-phase listeners, e.g. the `.origin` chip's navigation), not a bubble-phase one, or the suppression would arrive too late.
  - **Right-click is desktop's whole equivalent — no separate hover/kebab affordance.** `contextmenu` on a `.note-card` calls `e.preventDefault()` (blocking the native OS menu) and opens the same popover at the cursor position. Right-click never produces a compatibility `click` the way touch does, so no suppression is needed there.
  - **The popover is positioned above the touch/click point by default, flipped below and clamped to the viewport when there isn't room** — the same "don't render off-screen" discipline every anchored panel in this app follows (e.g. the project-switch dropdown).
- **Things established as intentional, not to be "fixed" without asking:** the tactile 3D press-down style on the primary button; the dark, minimal sign-in gate; pagination page sizes (see below) chosen deliberately for performance at scale.
- **Every value interpolated into an `innerHTML` template must go through `escapeHTML()`** — including URLs built from sheet data (e.g. a Drive-derived photo `src`), not just visible text. A URL/attribute value is exactly as capable of breaking out of its attribute as any other string; an audit found one such gap (an unescaped photo `src`) that has since been fixed. `window.open()` targets built from sheet data (`driveUrl`, etc.) should also go through a protocol allowlist (see `openSafeUrl()`), not be passed straight through.

## 7. Backend Rules

- **Every `doGet`/`doPost` must authenticate first** via `getCurrentUser_()` before touching any data. No action should read or write before this succeeds.
- **"This token is invalid" and "I could not check the token right now" are different answers, and collapsing them signs people out for no reason.** `verifyIdToken_` used to treat ANY non-200 from Google's `tokeninfo` as `'não autenticado'`. That endpoint is rate-limited, and this app calls it on *every* request — so a large photo batch (three concurrent uploads plus their row writes) can earn a 429, which the frontend then read as a dead session: token cleared, sign-in screen, every upload still in flight abandoned. Reproduced live on a 61-photo batch. Only a verdict from Google that the token itself is bad (400/401) is an auth failure; 429, 5xx, a JSON parse failure or a thrown fetch are all transient and now throw `'Servidor ocupado, tente novamente.'`, which the client retries like a network blip (`isBusyError`). **Reusable pattern:** any dependency you consult to authorize a request will eventually be slow, rate-limited, or down — and "I couldn't verify" must never be mapped onto "you are not who you say you are." Decide explicitly which upstream statuses are verdicts and which are outages, and treat only the verdicts as authentication failures.
- **An action whose cost scales with the number of ids must be chunked by the client, and given a request budget to match.** `deletePhotos`/`deleteDocumentos` trash one Drive file per id, so deleting a task that held ~60 photos meant ~60 sequential Drive calls plus the resolution reads — well past the client's 30 s deadline, which then retried twice and surfaced "não consegui excluir" after a minute and a half. `DELETE_CHUNK_SIZE` (12) keeps every request small and bounded, and each chunk that lands is durably done, so a failure part-way through leaves the earlier chunks deleted rather than rolling everything back. `SLOW_ACTIONS` in `sheetsPostRaw` gives delete/rename their own longer deadline on top of that. **Reusable pattern:** before adding a backend action that takes a list, ask what one element costs server-side and cap the list at whatever keeps the request comfortably inside the deadline — an unbounded list is a timeout waiting for a big enough user.
- **Error responses must use `err.message`, not `String(err)`.** `String()` on a real `Error` object prepends `"Error: "`, which silently breaks the frontend's exact-string matching between auth errors, permission errors, and generic errors. This was a real, previously-shipped bug — do not reintroduce it.
- **The frontend's permission-error detection matches by PREFIX, not exact string.** `isPermissionError()` in `index.html` treats any message starting with `sem permissão` or `sem acesso` as a permission denial. This was previously an exact-string `Set` keyed to `'sem permissão para escrever'` — a message that stopped being thrown the moment the hardcoded-role model was replaced by the `Papeis` matrix (which throws `'sem permissão para ' + action` instead), so every permission denial silently fell through to a generic "try again" message for a rejection that would never succeed on retry. `AUTH_ERROR_MESSAGES` (a different, still-exact-string `Set` for `getCurrentUser_`'s identity failures) is fine as-is — those messages are few, fixed, and unlikely to be touched incidentally. **Reusable pattern:** for an open-ended or growing family of backend error messages (like per-action permission strings), match the frontend on a stable prefix/code, not the exact wording — an exact match silently stops matching the next time someone rewords or adds a message on the backend side without realizing a frontend string comparison depends on it.
- **Row-level writes:** identify the target row by `id` in column A; update in place if found, append if not. Never rewrite an entire tab for a single-row change on the row-level tabs listed in Section 5.
- **Conflict handling:** check every row in a batch for a stale `lastModified` **before** writing anything in that batch (all-or-nothing), not after partial writes.
- **Concurrency:** the **write** path of `doPost` is wrapped in `LockService.getScriptLock()` to prevent simultaneous requests from interleaving badly. `verify` and `getAll` are deliberately **outside** that lock — a read has nothing to serialise against, and holding the write lock for the duration of a full multi-sheet read meant one person's sign-in blocked everyone else's saves. `getAll` still takes the lock *briefly*, for the id-backfill pass only (see below), and releases it before reading any data. **`uploadFile` is also outside the lock** — it touches only Drive, never a sheet, so it has nothing to serialize against; it used to sit inside the same lock as `batchMulti`/`saveSheet`/`renameProject`, which meant every upload queued behind every other upload AND behind the user's own task/entry saves, and was the stated reason concurrent client-side uploads kept getting declined (see Section 9's now-retired "concurrent uploads" entry — parallelising the client used to just relocate the wait into lock contention). Moving it out is safe for the same reason it always was: the file `uploadFile` creates isn't visible anywhere in the app until a later `batchMulti` (still fully locked) attaches it to a Fotos/Documentos row, and that step independently re-resolves the row's real section from its own `refTipo`, never trusting what `uploadFile` was told. `deleteFile` stays inside the lock — it reads sheets to resolve the file's real section/project.
- **`readSheet_` must never write.** It used to stamp missing `id`s as a side effect of reading, and the write-back was `range.setValues(values)` over the **entire** range — every column of every row, from a snapshot taken before the mapping loop. That is a read-modify-write across data a concurrent `batchMulti` may have changed in between: a row deleted between the `getValues()` and the `setValues()` would be resurrected by the stale write-back. It was survivable only because the whole of `getAll` sat inside the write lock — so the moment `getAll` was moved off that lock for latency, the write-back had to go with it. Assigning ids is now a separate, explicit `backfillMissingIds_(key)` pass that touches **only column A**, runs once per sheet inside a short-lived lock at the top of `getAll`, and leaves the actual reads lock-free and side-effect-free; `readSheet_` still fills a blank id in its returned object so the row is usable, but never persists it. **Reusable pattern:** a read path that mutates is a read path that has to be serialised, so keep repair/migration work in its own named, explicitly-invoked pass instead of hiding it inside the reader — and never write back a whole range to persist a change to one narrow column, since the write silently carries the rest of your stale snapshot with it.
- **Any column that ever holds a date-shaped string, or a value Sheets might reformat as one, must be defended on READ — writing a plain string is not enough.** `Range.setValues()` applies the same auto-parsing Sheets uses for manual typing: a string like `"2026-09-01"` written into a cell with no explicit text format can get silently reinterpreted as a real Date-typed cell, so a later `getValues()` on that same cell returns a JS `Date` object instead of the string the app wrote. `fmtDate_`/the `data` column special-case in `readSheet_` already existed to guard against exactly this — but `Tarefas.prazo` (the task deadline, also a plain `yyyy-MM-dd` string) was never given the same treatment, and a real user hit it: a `Date` object flows untouched into `JSON.stringify`, which serializes it as a full ISO timestamp (`"2026-09-01T00:00:00.000Z"`), and the frontend's `parseDateLocal()` (`str.split('-').map(Number)`, expecting exactly 3 parts) turns that into `NaN` → an Invalid Date → `"NaN/NaN/NaN"` wherever the deadline is displayed, and a blank/rejected native `<input type="date">` when editing it (native date inputs require exactly `yyyy-MM-dd`, not a timestamp). `readSheet_` now applies `fmtDate_` to `prazo` too, same as `data`. **The same gap existed for `criadoEm`/`lastModified`**, which must always be plain millisecond numbers — a `Date`-typed cell there (only reachable if that column's own number format is ever accidentally inherited from elsewhere, since the raw integer content itself doesn't trigger Sheets' auto-detection the way a date-shaped string does) would serialize to an ISO string that breaks arithmetic sort (`a.criadoEm - b.criadoEm` → `NaN`) and — worse — permanently false-conflicts every write to that row, since `buildRowIndexes_` (used by `findConflicts_`) reads `lastModified` directly off the sheet, bypassing `readSheet_` entirely, and a `Date`'s default `String()` (`"Mon Sep 01 2026 ..."`) can never equal the client's numeric baseline. Fixed with a second, narrower helper, `coerceTimestamp_` (unwraps a `Date` via `.getTime()`, passes anything else through untouched), applied both in `readSheet_` and in `buildRowIndexes_`'s direct read. **Reusable pattern:** when a defensive read-side coercion is added for one column because Sheets can silently change a cell's underlying type, audit every OTHER column of the same shape (date-strings, numeric timestamps) across every sheet, not just the one that happened to surface a bug report — the same class of corruption is latent anywhere the fix wasn't also applied, and it tends to stay invisible until enough time (or enough manual spreadsheet editing) passes for Sheets to actually reinterpret that specific cell.
- **Existence checks read column A only.** `assertBatchAccess_`'s create-vs-edit resolution uses `idExists_`/`existingIdSet_` (a per-request-cached `{id:true}` map built from column A) rather than a full `readSheet_` of every touched sheet, and `findConflicts_`/`applyBatch_` share one `buildRowIndexes_(ops)` pass (one id + `lastModified` read per touched sheet) instead of re-reading per op. The security property is unchanged — create-vs-edit is still resolved from the sheet's own state, never from client input — but a batch no longer costs a full-sheet read per operation.
- **Backups:** a time-based trigger (`installDailyBackupTrigger`, run once manually to install) copies **both** spreadsheets daily into a `Backups` folder in Drive — the business data AND the separate Usuarios/Papeis auth file (`Backup Usuarios <date>`) — pruning copies older than 30 days. The auth file was missing from this for a long time: it is the entire access-control configuration, and losing or corrupting it locks everyone out (correctly, since every check fails closed) with nothing to restore from. Its copy is best-effort and separate, so a failure to copy it can never cost the business-data backup. This must be manually re-installed if ever removed — it is not automatic on deploy.
- **Deployment discipline:** neither editing `Code.js` in the script editor NOR pushing to `backend/**` on `main` takes effect for the live Web App on its own — `clasp push` (or a manual editor save) only updates the script project's *source*; the `/exec` URL keeps serving whatever deployment version it was last pointed at until that deployment is explicitly redeployed to the new version. This exact gap — source updated, live URL still serving old code — has been the root cause of multiple confusing bugs in this project's history, including a real outage where a security fix's frontend half went live but the backend half didn't, breaking login for everyone. `deploy-backend.yml` now automates the redeploy step too (`clasp update-deployment` against the one existing deployment, right after `clasp push`), so a push to `main` alone is sufficient again — but if a change is ever made by hand directly in the Apps Script editor instead of through a commit, it still needs a manual redeploy (Deploy → Manage deployments → Edit existing deployment → "New version" → Deploy). Always suspect this first when backend changes don't seem to take effect, especially after any manual editor changes.
- **A green backend deploy does NOT by itself prove the backend changed — check the `clasp push` output, not the job's exit status.** `clasp push` exits 0 even when it uploads nothing. Specifically: when `appsscript.json` is among the changed files it asks "Manifest file has been updated. Do you want to push and overwrite?", and its `confirmManifestUpdate()` returns `false` immediately whenever `process.stdout.isTTY` is false — which it always is on a CI runner. It then prints `Skipping push.` and exits **successfully**. `clasp update-deployment` afterwards happily cuts a new version from the *unchanged remote source*, so the version number climbs and the workflow goes green while the live code is untouched. Worse, it is self-perpetuating: once the local manifest differs from the remote one, every subsequent push is skipped the same way, forever.
  - **This caused a real production outage.** A one-line manifest `timeZone` change froze the backend source across three consecutive "successful" deploys (versions 21, 22, 23). Nobody noticed until the frontend started calling a backend action (`verify`) that only existed in source which had never landed — every user got `Ação desconhecida: verify`, which isn't a recognized auth error, so login failed for everyone with the generic "Não consegui entrar. Tente novamente."
  - **Both halves of the fix are load-bearing:** `clasp push --force` (mandatory in CI — the confirmation prompt exists for interactive safety and a runner can never answer it), AND an explicit assertion on the push output that fails the job on `Skipping push.`, on `Pushed no files`, or on any output that doesn't positively confirm a push or a genuine no-op. `deploy-backend.yml` also now triggers on changes to itself and offers `workflow_dispatch`, so a pipeline fix actually re-runs the pipeline and a bad deploy can be re-run by hand.
  - **Reusable pattern, and the real lesson:** never let a deploy step's *exit code* stand in for evidence that the deploy happened. A CLI that prompts interactively will usually take the safe branch in CI and still exit 0 — so any deploy pipeline must assert on what the tool actually reported doing, and fail closed when it can't confirm it. Applies well beyond clasp: the general shape is "green pipeline, unchanged production," and it is invisible until something depends on the change that never shipped.
- **OAuth scopes:** the script needs `spreadsheets`, `drive`, `script.external_request` (for `UrlFetchApp` calls to verify tokens), and `userinfo.email`. If these are not explicitly declared in `appsscript.json`'s `oauthScopes`, Apps Script's automatic scope detection has previously been unreliable across edits — explicit declaration is safer. **NEEDS VERIFICATION:** whether `oauthScopes` is currently explicitly declared in the live `appsscript.json` or still relying on auto-detection.

### Security practices established (from a full security audit; reusable in future apps on this stack)
- **Reads never go over GET.** A bearer `idToken` must never travel in a URL/query string (server logs, browser history, proxies can all capture it) — `getAll` is `POST`, same as writes. `doGet` is kept only because Apps Script requires it to exist; it must stay an inert no-op, not a second read path.
- **Every free-text value written to a sheet cell is run through `sanitizeCell_()`** (prefixes a value starting with `=+-@` with a leading apostrophe) before `setValues()`. Without this, a value planted through the write API becomes a live formula the moment anyone opens the sheet directly or exports it — a real CSV/formula-injection vector, not hypothetical.
- **A whole-tab "clear and replace" write (`writeSheet_`) must never be used for data that is also access-scoped** (i.e. anything `hasProjectAccess_` filters). A project-scoped user's in-memory copy only ever contains what they're allowed to see, so replacing the whole tab with it silently deletes everything else. `saveProjetos_` is the pattern to copy: preserve out-of-scope rows, only replace the caller's own subset. `Tipos`/`Unidades` are fine to whole-tab-replace because they are genuinely shared, not access-scoped.
- **The client never names a Drive file. It names an app record.** `deletePhotos {ids}` / `deleteDocumentos {ids}` take record ids; the server resolves each row, authorizes it on both axes (section/action, then project), derives the `driveFileId` itself, trashes the file and deletes the row — all inside the one write lock. This *narrows* the attack surface rather than widening it: there is no longer any path where a client-supplied Drive identifier reaches `DriveApp`.
  - **This replaced a delete flow that could never work, and had never once deleted a file.** The client removed the row first (via `saveKey`) and then called `deleteFile`, but `deleteFile` refuses any `fileId` not present in `Fotos`/`Documentos` — the rule that stops an unchecked id reaching anything the deploying account can see. By then the row was gone, so every delete threw `arquivo não encontrado`, the error was swallowed client-side, and the file stayed in Drive forever. Two documented rules were in direct contradiction and the security rule silently won. Reproduced: deleting a task with 3 photos left all 3 live; deleting one photo left both.
  - **A parent-deletion cascade must delete the children FIRST**, while the parent still exists — the server authorizes a photo through its parent chain, so once the parent row is gone its photos can no longer be authorized.
  - `deleteFile` (single raw fileId) is kept for the legacy path and still applies the same present-in-a-sheet check. **Reusable pattern:** when a client operation needs a privileged resource handle, have it pass the *application* identifier and let the server derive the handle — a check that the client-supplied handle is "one of ours" is strictly weaker, and couples correctness to call ordering.
- **`sweepOrphanFiles(commit)` and `mergeDuplicateProjectFolders(commit)` resolve each project's folder BY ID (`resolveExistingProjectFolder_`), never by name.** They used to call `findProjectFolder_(p.id)` directly, so a project whose Drive folder had been renamed by hand — the exact case `driveFolderId` exists to survive — fell out of the `getFoldersByName` lookup entirely: the sweeper scanned nothing for it and reported a reassuring zero orphans while leftovers accumulated. Both now report an unresolvable project (`report.unresolved` / `report.skipped`) instead of silently skipping it. **`mergeDuplicateProjectFolders` additionally must never destroy a canonical folder:** it used to keep the OLDEST same-named folder, which trashed the folder `Projetos.driveFolderId` pointed at whenever the stored id happened to be a newer duplicate — and since it never repointed the sheet, every later upload landed inside a trashed tree and was purged 30 days later. It now prefers the folder the sheet actually points at over the merely-oldest one, never trashes any live project's canonical folder as somebody else's duplicate, and refuses (reporting, not guessing) when two live projects claim same-named folders. **Reusable pattern:** a repair tool operating on data the app depends on must treat the app's own pointer as authoritative — "pick the oldest" is a heuristic, and a heuristic that can delete the record of truth is a bug, not a policy.
- **`sweepOrphanFiles(commit)` reclaims files no row references.** Orphans come from uploads that reached Drive but whose row was never written (abandoned draft, app closed mid-batch) and — historically — from every delete, per above. It scans each project's root folder AND its `Fotos/`/`Documentos/` subfolders (a stray file can land directly in the project root — see the `uploadFile`/`kind` fallback in Section 3 — and `getFiles()` on a folder never recurses into subfolders, so scanning the root can't double-count what the subfolder scan already covers), only touches files older than `ORPHAN_MIN_AGE_MS` (24 h, so it can never race an upload in flight), and is **dry-run by default**: call `sweepOrphanFiles(true)` to actually trash. Idempotent, and Drive keeps trash for 30 days.
- **A function meant to be run manually from the Apps Script editor must not require an argument to actually take effect.** `sweepOrphanFiles`/`mergeDuplicateProjectFolders` both default to a dry run (`commit` falsy) — correct for safety, but the editor's "Run" button always calls the selected function with **zero** arguments, so a person running `sweepOrphanFiles` from the dropdown gets a real-looking, successful-looking report that silently deleted nothing, with no way to pass `true` through that UI. This produced a real, confusing support cycle: the underlying fix was correct and verified by tests, but "run it from the editor" could never actually commit anything. Fixed by adding zero-arg wrapper functions, `sweepOrphanFilesCommit()`/`mergeDuplicateProjectFoldersCommit()`, that just call the real function with `true` — safe to select and run directly, nothing else changed. **Reusable pattern:** any manually-run Apps Script function whose safe default is "dry run" needs a zero-arg "commit" wrapper alongside it, or a person using the only UI the editor offers can never reach the committing path at all.
- **`uploadFile` enforces a decoded-byte ceiling (`MAX_UPLOAD_BYTES`).** Photos previously had no size cap anywhere — not in the picker, not on the server — and since `uploadFile` runs outside the script lock, an authenticated client could push unbounded bytes at Drive.

## 8. Development Rules

- Preserve the existing architecture unless an architectural change is explicitly requested.
- Prefer the smallest change that solves the requested problem.
- Do not modify unrelated code.
- Do not introduce frameworks, dependencies, databases, or infrastructure unless explicitly requested.
- Do not create unnecessary tests or abstractions.
- When something is unclear, inspect the existing code rather than guessing.
- Before making significant architectural or authentication changes, explain the proposed change first and wait for confirmation.
- For investigation/debugging requests, investigate first and do **not** modify code unless explicitly told to.

### Testing permission changes
Any new or changed permission-controlled section needs a focused authorization test before it's considered done — not just a read of the code. There's no CI test suite for this app; the established way to do it (used for the section/action model's own security audits) is a throwaway Node script that loads the real, unmodified `backend/Code.js` into a mocked Apps Script environment (fake `SpreadsheetApp`/`CacheService`/`DriveApp` backed by an in-memory sheet, `UrlFetchApp.fetch` stubbed to simulate `tokeninfo` for controlled fake tokens) and drives it through real `doPost()` calls with crafted payloads and a fake, obviously-not-real sensitive value — never real business data. At minimum, verify for at least one role denied the new section: `getAll` never contains the value (including via any embedded/cross-page path like Fotos/Notas); manually forged permission/role claims in the request body are ignored; writes to the section are rejected and leave the sheet unchanged; and, separately, that authorized access still works (a pure "always denies" harness bug would otherwise look identical to success). Delete the throwaway script and any temp files afterward — nothing from this process belongs in the repo.

### Testing sync/conflict/timing races — a hand-rolled backend stub is not enough
A frontend-only test harness that stubs `batchMulti` with hand-written logic (even logic that correctly mirrors the real conflict RULE) can still completely miss a bug that depends on how `sheetSnapshot` got seeded — because a hand-rolled stub's test setup almost always seeds it from a real, just-fetched `getAll`, which is never stale by construction. This happened for real: a whole round of "fix the Tarefas checkbox race" work shipped, verified by 24 passing checks against exactly such a stub, and the underlying bug (a cache-first boot's write path racing its own unhydrated snapshot) was still live in production immediately after — the stub simply couldn't reach the code path where the bug lived.

**The fix was to test against the actual `backend/Code.js`, not a stand-in for it** — the same mocked-`vm`-context technique from "Testing permission changes" above, but driving the real, unmodified `index.html` in Playwright against it (route-intercept `https://script.google.com/**` and hand every request straight to `sandbox.doPost()`), so the REAL `buildRowIndexes_`/`findConflicts_`/`applyBatch_`/`readSheet_` run on every request. This is what turned "24 checks pass" into "the exact production toast reproduces, from a real cold `localStorage` cache seeded across two separate page loads, with real SIM/NAO round-tripping and real full-row rewrites" — and, just as importantly, what proved the fix by failing the identical script against the pre-fix commit (`git show HEAD:index.html` served from a second temp directory) before it passed against the fix.

**Reusable pattern for any bug involving `sheetSnapshot`, `lastModified`, caching, or timing:**
1. Reproduce against the real backend mock first, with a scenario that actually exercises the suspected timing window (a second page load from a cache written by the first, an injected network delay, a conflict engineered by mutating the mock sheet directly between requests) — not just "many rapid clicks," which a stub can pass for the wrong reasons.
2. Negative-control it: run the identical script against the previous commit's frontend and confirm it fails there. A repro that hasn't been shown to fail on the buggy code hasn't proven anything about the fix.
3. Only then treat a hand-rolled stub suite (the `tasks_test.js`/`phasea_test.js` style — fast, but with an idealized backend) as sufficient for everyday UX regressions; it is not sufficient on its own for anything touching conflict detection, caching, or boot-time sequencing.

### Testing background/async UI lifecycles
An upload/queue/optimistic-lifecycle change needs the same real-backend treatment as a sync/conflict change (above), plus one extra discipline: **the assertions must be about what the user can see and when, not just about the end state.** The upload pipeline's suite (throwaway, deleted afterwards) drove the real `index.html` in Playwright against the real `backend/Code.js` in a mocked Apps Script `vm`, and covered: an 18-photo batch rendering before any upload lands; the UI staying navigable mid-batch; a *hung* request (a route handler that never fulfils) proving files after it still complete and the batch still terminates; a forced server rejection proving per-file failure and retry; a metadata-save failure proving no lost Drive reference and that retry doesn't re-upload; deletion mid-flight patching the right record; the sheet never receiving a blank-`driveFileId` row even when the parent is saved mid-batch; the cache never holding an in-flight record; a full reload proving persistence; and a rapid-task-toggle regression proving the new row filter didn't disturb the existing sync queue. Negative-controlled against the previous commit's `index.html` served from a second directory, which confirmed both the blocking render and the permanently stuck toast. **Two harness lessons worth keeping:** Playwright matches routes in *reverse* registration order, so a `**/*` catch-all must be registered FIRST or it swallows every specific handler; and when the code under test legitimately retries a file, keying injected failures by request ordinal silently targets the wrong file — key them by a stable per-file identifier instead.

### A test that passes on the happy path can still be hiding the bug
Three of the worst defects in the photo subsystem were invisible to both code
review and a green test suite, because every existing test exercised a clean
sequence. Each needed a *combination* to show itself:
- **Deleting never removed the Drive file** — visible only if a test asserts on
  Drive state after a delete, not just on the sheet and the UI. Every test
  checked "the row is gone" and stopped there.
- **A background sync destroyed in-flight photos** — visible only by triggering
  a `getAll` *during* an upload. No test had ever overlapped the two.
- **A photo whose row write failed vanished on reload** — visible only by
  combining a failed persist with a relaunch *and no other write in between*.
  With any later write to the same tab, the photo is silently rescued and the
  test passes for the wrong reason.

**Reusable pattern:** when testing an optimistic/async subsystem, the valuable
cases are the *crossings* — an operation during a refresh, a failure followed by
a restart, a delete during an upload — and the assertions must reach every
system the operation claims to touch (state, sheet, **and** Drive), not just the
one that is easiest to read. A suite made only of clean sequences measures how
well the happy path works, not whether the system is correct.

### Token-efficient editing
- Before reading a large file, search for the specific code relevant to the requested change when practical.
- Read only the necessary surrounding context unless the task requires understanding the broader architecture.
- For localized changes, prefer targeted edits/replacements over rewriting or rereading the entire file.
- Use exact, sufficiently unique strings for targeted replacements to avoid unintended changes.
- Batch related changes into a single operation when practical.
- Avoid unnecessary file exploration, verbose explanations, redundant verification, or rebuilding code that doesn't need to change.
- For simple CSS/text/localized UI changes, don't reread the entire frontend file unless genuinely needed.
- For new features, architecture, authentication, backend changes, debugging, or ambiguous situations, prioritize understanding context correctly over saving tokens.
- Never sacrifice correctness or safety merely to reduce token usage.

## 9. Known Limitations / Important Decisions

- **Drive files are currently shared as `ANYONE_WITH_LINK` (view-only), not private.** This was explicitly identified as a security gap. A fix was designed (per-project `addViewer()`/domain-restricted sharing synced automatically with `Usuarios` role/project changes, with a manual "reconcile now" function rather than a scheduled job) but **not implemented**. Anyone possessing a direct file link can currently view it without going through the app's auth at all.
- **iOS standalone PWA cannot silently restore a session on a fresh (fully-closed) launch** — this is a confirmed platform limitation (separate WKWebView storage partition from Safari), not something fixable in this app's code. The app is designed to fail gracefully here (show the button immediately) rather than pretend otherwise.
- **Section/action permissions are role-based, not per-user.** All users sharing a role (e.g., all `partner` users) get identical `Papeis` capabilities. Per-user customization would require a new per-user override, layered on top of `sectionsForRole_()` — not currently supported, no current requirement for it.
- **`deleteFile` (Drive) is fully section- and project-scoped**, resolved server-side from the row itself (never client input) — same two-axis check (section/action, then project) as every other write path. A photo's real owning section/project come from `resolveFotoSection_`/`resolveFotoProject_` (which parent it's actually attached to); a document's from its own `projeto` column.
- **Entry-attached notes are the one nested feature requiring the two-tab (Notas ↔ parent entry) resolution logic described in Section 5** — any future data model change touching Notas or Fotos should account for this union/multi-hop structure rather than assuming a flat 1:1 relationship.

- Full CRUD for lançamentos (Caixa da Obra + Empreiteiro), tasks, notes (standalone + attached), photos, and documents.
- Google Sheets + Drive backend via Apps Script, replacing an earlier `window.storage`-based approach entirely.
- Row-level writes with conflict detection, locking, and daily backups.
- Google Sign-In authentication with backend-verified ID tokens.
- Two-axis authorization: project-level and section/action-level (role capabilities data-driven via the `Papeis` tab), both enforced server-side, independently of each other.
- Session-restoration UX tuned specifically for iOS PWA constraints (session hint, standalone detection, proactive foreground-return refresh).
- Cache-first loading, offline-tolerant reads, clear-fail writes, retry logic for transient network errors.
- **Perceived-performance pass ("time until useful"):** sign-in gated on a data-free `verify` call rather than the full `getAll`, cached data rendered immediately behind a fresh-permission filter, backend warm-up on sign-in button press, deferred cache writes, render-before-await on task add/toggle, and `getAll` moved off the write lock with reads made side-effect-free. Measured: gate opens in ~15–25 ms after the credential arrives even with `getAll` stubbed at 4 s.
- App-version update-check banner (dismissible, never forces a reload).
- Background photo/document uploads: files appear in the UI immediately (local preview + per-file upload state), upload with limited concurrency in the background (see `UPLOAD_CONCURRENCY` below), and can't leave the batch stuck on one slow or failed file. Progress lives in a persistent upload tray that survives navigation; every upload state is visually distinct and queued photos show their position in line.
- Photo deletion actually deletes: `deletePhotos`/`deleteDocumentos` trash the Drive file and remove the row in one server-side operation, with bulk selection in the album and an orphan sweeper for anything left behind.
- Photos and documents are routed into per-project `Fotos/`/`Documentos/` Drive subfolders (not dumped in the project root), and a project can have photos added directly to it (not just ones attached to a lançamento/tarefa/nota) via a "Fotos do projeto" album on the Docs page.
- Pagination throughout (Entries, Tasks, Notes, Docs, Fotos) — stress-tested at ~3,000-entry scale. Tarefas Concluídas gets its own smaller page size (`TASKS_DONE_PAGE_SIZE`, 10, vs. 40 for the other three task categories) and is sorted by `lastModified` (most recently completed first), not `criadoEm` — the other categories are the small actionable set someone needs to see in full, but a user's completed-task history is mostly old and someone rarely wants more than the last handful by default. **Reusable pattern:** for a "done/archived/history" list at scale, default to a short, recency-sorted slice with a "carregar mais" affordance rather than either the same page size as an actionable list or the item's creation date — recency of the terminal state (completion, closure) is usually what a user means by "recent" for a done-list, not when the item was first created.
- Mobile-focused UI polish pass (typography, shadows, transitions) — token-level, no layout changes.

**Not yet implemented / open work:**
- Private Drive file sharing (Section 9) — designed but not built.
- Per-user (rather than per-role) permission customization — not built, no current requirement for it.
- A user-management UI (the `usuarios` section in `Papeis`/`SECTIONS` is reserved for this but nothing reads/writes it yet).

**Deliberately not done (from the pre-production audit) — each a real trade-off, not an oversight, and not currently planned:**
- **`oauthScopes` left implicit in `appsscript.json`** (relies on Apps Script's auto-detection). Declaring it explicitly means enumerating every scope actually in use and could force the deploying account to re-consent — risking the exact "backend half of a change goes live, breaks something for everyone" failure this project has already hit once. Needs a deliberate, verified pass, not a guess. **This decision now carries more weight than when it was first deferred:** `deploy-backend.yml`'s `clasp push` runs with `--force` (see Section 7 — mandatory in CI, since the interactive confirmation prompt it replaces can never be answered on a runner), so any future edit to `appsscript.json`, including finally declaring `oauthScopes`, will push and redeploy automatically on the next commit to `main` with no human confirmation step in between. Whoever makes that change should watch the deploy and verify login immediately after, the same way this session did following the CI fix — don't assume "it pushed" means "it works."
- **A per-request backend read cache** (dedupe `readSheet_` calls within one `doPost`). Mostly moot after `syncSheets` stopped sending empty-diff ops — that removed the two full-sheet reads this would have targeted. Caching further inside the transactional write path (`findConflicts_`/`applyBatch_`) risks a subtler correctness bug for whatever's left to gain.
- **One unified `{ok, code, message}` response envelope** across every backend action (today each action's response shape is bespoke and every frontend caller already knows its own). Real value as a foundation for future apps, but reshaping every action and every caller on a live financial app isn't justified by today's problem — the permission-error prefix-match fix already solves the actual bug this would have prevented.
- **Caching Google's `tokeninfo` verification result** to cut the one outbound HTTPS call every request makes. Trades a small latency win for a real, if small, revocation-detection delay — needs an explicit decision, not a default.

## 11. CLAUDE.md Maintenance

Keep `CLAUDE.md` up to date. When a code change introduces or changes an important:

- Architecture decision
- Workflow or convention
- Security rule
- Development instruction
- Pattern or practice that should be replicated as a foundation for future apps

...update `CLAUDE.md` accordingly, in the same piece of work that makes the change (not as a separate follow-up to remember later).

Do not update it for trivial implementation changes or app-specific details that have no future value.

**Standing rule, permissions specifically:** any change to permission-related code or UI — a new page, a new subsection/widget, a new cross-cutting data type, or a change to which section governs something — must, in the same piece of work: update the "Current permission map" table and the `SECTIONS`/`VIEW_FILTERED_SECTIONS` description in Section 4; add an explicit `SIM`/`NAO` row in the `installPapeisSheet()` seed for **every** defined role, not just the ones being granted access, whenever the set of valid `(role, section)` keys changed; and run a focused authorization test (Section 8, "Testing permission changes") with at least one role denied the new/changed section before calling it done. The permission map is only useful if it's never allowed to drift from what the code actually enforces, and a section is only as deny-by-default as the last time someone actually tried to bypass it.
